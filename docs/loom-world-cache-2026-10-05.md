# V3의 반복 인덱스 준비 비용

기존 V3는 AST 추출 결과를 파일별로 캐시했다. 하지만 Snapshot을 만들 때
Revision 계산과 파일 목록 계산을 각각 수행하며 파일을 다시 읽고 해시했고,
CodeGraph가 다시 소스를 읽고 해시한 뒤 캐시된 심볼로 모든 인덱스를 조립했다.
따라서 파싱 캐시가 있어도 같은 저장소를 다시 여는 비용이 컸다.

## 변경

World는 `.loom-v3/file-digests.json`에서 파일 해시를 재사용한다. 디렉토리는
실제로 조회하여 추가·삭제를 감지하고, Unix에서는 크기, mtime/ctime의 나노초,
device/inode, mode가 모두 같을 때만 기존 해시를 사용한다. 이 정보를 제공하지
않는 플랫폼에서는 파일을 다시 해시한다. Snapshot의 Revision은 같은 파일 표에서
기존과 동일한 규칙으로 계산하므로 중복 순회가 사라졌다.

완성된 그래프는 `.loom-v3/world-graph.json`에 저장한다. 지원 언어의 상대 경로와
내용 해시, 그래프/추출 형식 버전이 같으면 인덱스 전체를 불러온다. 문서 변경은
파일 표와 Revision을 갱신하지만 코드 그래프를 무효화하지 않는다. 코드가 바뀌면
기존 파일별 AST 캐시를 먼저 확인하고 실제 추출이 필요한 파일만 읽는다.

두 새 캐시는 각각 최신 상태 한 개를 원자적으로 교체한다. 격리 사본은 자신의
파일 표·완성 그래프를 사용하며 기존 공유 AST 캐시를 활용한다. 캐시 JSON 저장은
버퍼를 사용한다. 버전 불일치나 해석할 수 없는 캐시는 원본으로부터 재생성한다.
워커 검색의 파일 표에도 같은 해시 캐시를 적용했고, 읽은 근거가 Snapshot의
해시와 다르면 오래된 근거로 사용하지 않는다.

승인과 원본 변경 검사의 `Revision::capture`는 계속 실제 파일 내용을 해시한다.
캐시를 승인 근거로 대체하지 않았다. 단순 디렉토리 목록은 기존처럼 AST를 만들지
않고 조회한다. 파일 변경 감지와 검색 결과 내용 읽기는 여전히 수행한다.

## 실제 저장소 측정

같은 저장소에서 모델 호출 없이 World::open만 측정했다. 빌드는 debug 심벌과
증분 컴파일을 끈 unoptimized 설정이며, 수정 전에도 파일별 AST 캐시는 있었다.
구현 변경으로 측정 시 파일/심볼 수는 조금 다르다.

| 측정 | 파일 | 심볼 | 시간 |
|---|---:|---:|---:|
| 수정 전 3회 | 10,240 | 142,510 | 22.335 / 22.736 / 20.331초 |
| 수정 후 변경된 소스 4개 반영 | 10,241 | 142,558 | 20.295초 |
| 수정 후 변경 없는 재조회 2회 | 10,241 | 142,558 | 6.714 / 7.341초 |

재조회에서는 파일 내용 해시 0개, AST 추출 0개, 완성 그래프 재사용을 확인했다.
이 수치는 인덱스 준비 비용이며 전체 에이전트 실행 시간의 측정 결과가 아니다.
캐시를 지우거나 소스를 바꾼 첫 실행은 준비 비용이 남는다.

실제 사용되는 release 설정에서도 별도로 측정했다. 새 문서/보고서 2개가 추가된
10,243개 파일에서 1.481 / 1.187 / 1.212초였으며, 변경 없는 두 재조회는 파일
내용 해시 0개·AST 추출 0개·완성 그래프 재사용이었다. release의 수정 전 기준선은
측정하지 않았으므로 앞의 unoptimized 기준선과 속도 배수로 비교하지 않는다.

변경 없는 재조회·새 프로세스·문서 변경·소스 추가/수정/삭제·같은 크기 편집 후
mtime 복원·파일 교체·오래된 근거 거부·캐시 손상/버전 변경을 회귀 검사했다.
V2 23개, V3 55개, TUI 229개 테스트와 화면 검사 456개가 통과했다. release
PTY에서 V2/V3 조회, 병렬 실행, 수정/승인/재검증, 계획 복구도 통과했다.
