# HTTP 재현 테스트의 모델 목록 캐시 오염 복구

## 原因と影響

503 복구 검사용 loopback 서버가 `{"data":[{"id":"auto"}]}`를 반환했다.
모델 탐색 캐시가 서버 주소와 인증 정보를 구분하지 않고
`~/.loom/cache/omniroute-models.json` 한 파일에 저장했기 때문에, 테스트가 실제
사용자 목록을 덮어썼다. 이후 새 Loom은 10분 동안 테스트 목록을 재사용했고
개별 모델을 선택할 수 없는 상태가 됐다. 이전 검증은 작업 복구만 확인했으며
사용자 모델 캐시 보존을 확인하지 않아 이 부작용을 놓쳤다.

사용자의 문제 제보 뒤 파일 내용을 확인해 원인을 확정했다. 키 파일과 공급자
연결은 삭제되지 않았다. 관리 API에서도 연결 15개가 남아 있고 12개가 활성
상태였으며, 비활성 연결을 임의로 켜거나 바꾸지 않았다.

## 복원과 수정

- 오염된 파일을 별도 이름으로 보존하고 실제 서버에서 목록 1,183개를 다시 받았다.
- 서버 URL과 인증 키를 SHA-256으로 식별해 각각 별도의 캐시 파일을 사용한다.
  키 원문은 파일 이름에 넣지 않는다. 뒤의 `/` 유무는 같은 서버로 처리한다.
- 출처를 확인할 수 없는 기존 단일 캐시는 새 코드에서 읽지 않는다. 이전
  바이너리를 위한 기존 파일도 실제 목록으로 복원했다.
- 캐시 쓰기는 같은 디렉토리의 임시 파일을 원자적으로 교체한다. 다른 Loom이
  동시에 읽는 도중 일부 JSON만 보게 되는 것을 막는다.
- `LOOM_MODEL_STATE_DIR`로 모델 캐시와 사용 기록을 분리할 수 있게 했다.
  미지정 시 기존 `~/.loom` 경로를 유지하며, API 키를 읽는 위치는 변경하지 않는다.
- HTTP 재현 테스트는 이 경로와 `LOOM_SETTINGS_STATE_DIR`를 임시 폴더로 지정한다.
  호출용 키와 관리용 키도 테스트 값으로 지정하며 실제 사용자 키를 쓰지 않는다.

## 검증

- 서버·인증 키별 캐시 구분 검사는 수정 전에 실패하고 수정 후 통과했다.
- 서로 다른 실제 loopback HTTP 서버의 목록을 같은 캐시 디렉토리에 저장한 뒤,
  양쪽 서버를 종료하고 각각의 캐시 목록을 다시 읽어 서로 섞이지 않음을 확인했다.
- HTTP 503 실제 터미널 재현이 다시 통과했고, 실행 전후 실제 사용자 목록 파일
  전체의 해시와 파일 목록이 동일했다. 테스트 캐시와 사용 기록은 임시 폴더에 생겼다.
- 첫 해시 비교 실행은 실제 목록을 생성하는 다른 진단 프로세스와 겹쳐 파일
  추가를 감지했다. 진단 완료 후 순서대로 재실행해 사용자 캐시 보존을 확인했다.
- 실제 gateway에 연결한 배포용 TUI의 모델 선택 화면도 확인했다. Antigravity,
  Gemini, Groq, OpenRouter 등의 그룹과 개별 모델 수가 다시 표시됐다. 목록
  확인만 했으며 모델 추론을 호출하지 않았다.
- Core 233개·TUI 238개 테스트, 화면 검사 583개, dev/release 빌드 통과.
  제외된 수동 환경 검사는 Core 1개·TUI 3개이며 실패는 없다.

현재 실행 중인 Loom은 시작할 때 읽은 목록을 유지한다. Ctrl+Q로 종료한 뒤
`scripts/loom-v3`로 다시 시작해야 새 캐시 구조와 복원된 선택 목록이 적용된다.
