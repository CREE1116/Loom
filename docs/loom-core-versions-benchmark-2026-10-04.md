# Native Core V1 / V2 / V3 비교와 TUI 연결

2026-10-04에 같은 Rust 과제 12개를 세 코어로 실행했다. 별도 저장소에서 수정하고,
원본이 승인 전에 그대로인지 확인한 다음 승인·재검증·숨은 테스트로 채점했다.
V1은 `loom-core`, V2는 `loom-core-v2`, V3는 `loom-core-v3`다. Codex 자체는 이 비교에 포함하지 않았다.

## 결과

새 실행 식별자를 넣은 전체 비교의 결과다. 합계는 실패한 실행도 포함한다.

| 코어 | 숨은 테스트 통과 | 모델 요청 합계 | 입력 토큰 합계 | 출력 토큰 합계 | 작업 시간 합계 |
| --- | ---: | ---: | ---: | ---: | ---: |
| V1 | 12/12 | 57 | 121,174 | 23,724 | 311.369초 |
| V2 | 10/12 | 24 | 43,503 | 28,765 | 279.100초 |
| V3 | 11/12 | 43 | 46,032 | 30,397 | 308.621초 |

세 코어가 모두 통과한 10개만 비교하면 다음과 같다.

| 코어 | 모델 요청 | 입력 / 출력 토큰 | 작업 시간 합계 |
| --- | ---: | ---: | ---: |
| V1 | 46 | 97,018 / 13,632 | 208.660초 |
| V2 | 20 | 36,250 / 18,065 | 188.999초 |
| V3 | 35 | 37,097 / 20,099 | 215.022초 |

V2·V3의 사전 맥락 제공은 이 과제들에서 입력과 모델 호출을 줄였다. 출력은 증가했다.
전체 품질은 V1이 가장 높았다. V3가 항상 빠르거나 V2보다 정확하다고 결론 내릴 수는 없다.
이 12개는 작은 단일 crate 수정 과제라 큰 저장소의 탐색·그래프 분할 성능이나 Codex급
종합 성능을 증명하지 않는다. 이번 과제에서는 실제 병렬 워커 효과를 측정하지 않았다.

초기 전체 비교는 V1 12/12, V2 11/12, V3 10/12였다. 일부 요청이 수십 ms에 반환돼
게이트웨이 응답 재사용 가능성이 있었다. 이를 확정할 공급자 기록은 없어 초기 실행의
시간은 속도 결론에 사용하지 않는다. 이후 과제별 고유 실행 식별자를 시스템 요청에
넣고 세 엔진에는 같은 식별자를 전달했다. 정상적인 프롬프트 캐싱은 차단하지 않았다.
두 전체 비교를 합친 통과 수는 V1 24/24, V2 21/24, V3 21/24다.

## 실패를 판정한 근거

- 새 비교의 V2 `average-empty`: 공개 검증과 승인은 통과했지만 숨은 동작 검사 실패.
  초기 비교에서는 V3가 같은 과제에 실패했다. 검증된 제안도 동작 회귀를 놓칠 수 있다.
- V2 `token-bucket`: 두 응답이 모두 `MaxTokens`로 끝났고 실제 `parts`가 빈 배열이었다.
  공급자는 각각 3,934 / 3,939 출력 토큰을 보고했지만 편집·답변은 없었다. Core는 이를
  `model returned ungrounded prose twice`로 잘못 설명했다. 출력 상한/내부 추론 소진이
  원인일 가능성이 있지만 공급자가 추론 세부 내역을 보고하지 않아 확정할 수 없다.
- V3 `token-bucket`: 두 시도에서 유효한 편집과 완료를 만들지 못했다. 성공으로 표시하지 않았다.
- V1은 12개 모두 승인 후 숨은 테스트를 통과했다.
- 두 전체 비교의 72개 실행 모두 승인 전 원본 바이트가 유지되었다.

벤치 바이너리는 실행 전에 복사·고정했고 SHA-256을 JSON에 남겼다. 이후 TUI 수정과
V3 중단 상태 분류 수정은 이 고정 바이너리에 포함되지 않는다. V3가 검증 실패가 아닌
작업 미완료를 `ValidationFailed`로 표시하던 것은 현재 코드에서 `Unresolved`로 바로잡았다.
벤치 실패를 숨은 답으로 맞추거나 결과 JSON을 사후 수정하지 않았다.

## 실행 조건과 재현

- 요청 모델: `omniroute/agy/gemini-3.1-pro-high`.
  성공한 응답의 실제 공급자 모델은 모두 `omniroute/antigravity/gemini-3.1-pro-high`였다.
- 공통 공급자 ModelPort, 명시적 모델 고정, 실행당 모델 요청 상한 8, 시도 상한 2.
- Core 시간 상한 110초, 프로세스 외부 상한 120초. 두 과제를 동시에 실행하며
  과제 안에서는 세 코어의 실행 순서를 회전했다.
- 동일한 오프라인 Cargo.lock을 사전 생성하고 숨은 테스트는 승인 후 추가했다.
- 작업 시간은 격리·모델 대기·공개 검증을 포함한다. 별도 승인 재검증과 숨은 테스트
  시간은 표에서 제외했다. 공급자 변동과 다른 로컬 작업 때문에 정밀 속도 벤치는 아니다.
- 토큰은 공급자가 보고한 값이다. 캐시 사용량은 공급자가 보고하지 않아 모른다.
  게이트웨이 내부 재시도 요청 수는 Core 모델 요청 수에 포함되지 않을 수 있다.

```sh
cargo build --manifest-path custom-tui/Cargo.toml
scripts/loom-corebench --model omniroute/agy/gemini-3.1-pro-high \
  --json /tmp/loom-core-comparison.json
# 특정 과제를 여러 번 비교
scripts/loom-corebench --model MODEL --only token-bucket average-empty \
  --repeat 3 --json /tmp/loom-core-repeated.json
```

[고유 식별자 전체 결과](../bench/core-versions/results/2026-10-04-unique-reference.json),
[초기 전체 결과](../bench/core-versions/results/2026-10-04-initial.json),
[단일 과제 파일럿](../bench/core-versions/results/2026-10-04-pilot.json).
JSON의 임시 디렉터리에는 실행 로그·제안·승인·숨은 테스트 출력을 보존했다.
임시 디렉터리는 운영체제가 나중에 지울 수 있으므로 장기 근거는 저장소의 JSON을 사용한다.

## TUI에서 사용

```sh
scripts/loom --backend v1 --model MODEL  # 기존 Native, native도 같은 선택
scripts/loom --backend v2 --model MODEL
scripts/loom --backend v3 --model MODEL
```

`MODEL`에는 실제 사용 가능한 모델을 지정한다. 벤치에서 확인한 경로는 위의 Gemini 경로다.
기존 기본 엔진을 임의로 교체하지 않았다. V2/V3는 시작 명령의 `--backend`로 선택한다.
실행 중 코어를 바꾸려면 종료하고 다시 시작한다. 이미 열린 Loom도 Ctrl+Q 후 재시작해야 한다.

- `:edit 요청`: 격리 사본 수정 → Core 검증 → 실제 승인·거절 선택지.
- `:analyze 요청`: 읽기 전용 분석. 파일을 고치지 않았다는 이유로 실패 처리하지 않는다.
- `:inspect 요청`: 읽기 전용 조회. V2의 `list 경로`, `read 경로`, `search 검색어`,
  `check`는 모델 요청 없이 실행한다.
- `:chat 요청`: 저장소 도구 없이 직접 대답한다. 자동 의도 추정이 맞지 않을 때 접두사를 쓴다.
- 검증 명령을 직접 정하려면 `--core-check 'cargo test --offline --manifest-path 경로/Cargo.toml'`.
- Esc는 모델 실행과 승인 중 재검증을 취소한다. 종료는 작업 스레드의 모델 응답을 기다리지 않는다.
- 미승인 제안은 재시작 시 복원한다. 원본이 바뀌면 승인 적용을 거부하고 거절할 수 있게 유지한다.

## 연결 구조와 현재 한계

`backend/version_core.rs`는 세 코어와 공급자 프로토콜을 번역하고 실제 모델·토큰·시간을 관측한다.
`backend/versions.rs`는 V2/V3 실행을 배경 스레드에서 시작하고 공통 UI 이벤트로 투영한다.
Core가 격리·검증·승인을 소유한다. TUI는 새로운 Core 작업 루프를 구현하지 않는다.
V3에는 독립 `Validator` 인터페이스를 추가해 TUI 실행 정책을 실제 검증 프로세스에 적용했다.

V3의 SplitGate는 후보를 계산하지만 하위 워커를 디스패치하지 않는다. TUI도 단일 실행으로
표시한다. 실제 그래프 기반 병렬 작업은 별도로 구현·검증해야 한다. 이미지·스킬 등 지원하지
않는 입력은 조용히 버리지 않고 명시적으로 거부한다. 대화 요청은 현재 턴만 모델에 전달한다.

## 검증 기록

TUI 전체 테스트 223개 통과(외부 창/환경 테스트 3개 제외), 자체 화면 검사 442개 통과,
기존 PTY 검사와 V2/V3의 실제 수정·재시작·승인 PTY 검사가 통과했다. V2 테스트 18개,
V3 테스트 15개도 통과했다. debug 및 release 빌드를 완료했다.

V3의 `cargo clippy --all-targets -- -D warnings`는 33개 lint로 실패했다. 대부분 중첩
조건문, 불필요한 참조·format 등 정리 항목이며, 이번 연결 작업에서 전체 코어의 문체를
일괄 변경하지 않았다. 테스트 통과가 엄격한 lint 통과를 뜻하지는 않는다.
