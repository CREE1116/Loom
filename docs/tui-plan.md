# Loom TUI 초기 기획

> 현재 구현 체크리스트: [TUI 완성 계획](tui-completion-plan.md).

> 후속 확정 설계: [Custom CLI 구현 기획서](orchestrator-implementation-plan.md). 이 문서는 초기 TUI 논의와 구현 경과를 보존한다. 최종 목표는 Codex 코어를 단계적으로 자체 Core와 자체 Runtime으로 완전히 교체하는 것이다. 아래의 하위 에이전트 관제·Codex 코어 유지 설명은 과도기 UI 범위이며, 최종 orchestration 설계는 후속 기획서를 우선한다.

상태: 논의용 초안. 사용자가 새 Rust 화면 처리 엔진, 대화·관제 혼합 방향, 조작감 우선순위, 클릭 조작, 에이전트별 별도 터미널 창을 제안했다. 세부 화면과 키 배치는 아직 확정하지 않았다.

## 목표

Codex 코어를 유지하면서 새로운 Rust 화면 처리·입력 엔진을 만든다. 익숙한 CLI처럼 대화를 읽고 지시하기 편하며, 작업과 에이전트 상태를 필요할 때 펼쳐 확인할 수 있어야 한다. 사용자가 원하는 체감 기준은 Claude Code처럼 읽기 편하고 인터랙션이 자연스러운 화면이다. 특정 제품의 내부 구조나 단축키를 그대로 복제한다는 뜻은 아니다.

첫 버전의 완료 기준은 새 엔진을 통해 실제 Codex 세션을 시작·재개하고 작업을 끝까지 수행하는 것이다.

## 구현 기반

- 현재 소스 기준: `8ea2428c38f8994e18d789669f5cbc5df75e1f17`.
- 기존 `codex-rs/tui`는 동작과 호환성의 참고 구현으로 사용한다. 새 엔진은 기존 TUI의 화면·입력 상태 머신에 종속되지 않는다.
- 저수준 터미널 입출력 라이브러리 활용은 새 엔진과 양립한다. 제안은 Crossterm을 터미널 경계에 두고, 화면 모델·갱신·입력·포커스·오버레이를 직접 구현하는 것이다. Ratatui 사용 여부는 아직 확정하지 않았다.
- `app-server-client`를 통해 코어에 연결한다. 기존 TUI의 `app_server_session`은 요청·응답 처리의 참고 구현으로 사용한다.
- 화면 표현과 사용자 조작부터 변경한다. 코어 교체와 새 백엔드는 후속 단계다.
- 원본 빌드·실행 확인은 구현에 앞서 필요하며, 아직 수행하지 않았다.

## 첫 버전의 사용 흐름

1. 작업 폴더에서 시작하거나 기존 세션을 재개한다.
2. 여러 줄 지시와 파일 참조를 입력한다.
3. 응답과 도구 실행을 실시간으로 확인한다.
4. 승인 요청의 대상·내용·범위를 확인하고 허용하거나 거절한다.
5. 파일 변경과 실행 결과를 검토한다.
6. 추가 지시를 보내거나 실행을 중단한다.

## 화면 방향 후보

| 후보 | 기본 화면 | 장점 | 비용 |
| --- | --- | --- | --- |
| 대화 중심 | 넓은 대화 + 입력창, 상세는 필요할 때 열기 | 작은 터미널에서도 읽기 쉽다 | 작업 상세를 열어야 한다 |
| 작업 공간 중심 | 대화 + 도구·파일·diff 상세 패널 | 진행과 변경을 함께 확인한다 | 좁은 창에서 패널 전환이 필요하다 |
| 관제 중심 | 작업·에이전트 목록 + 선택한 세션 | 여러 작업의 상태를 확인한다 | 선택·포커스·알림 설계가 복잡해진다 |

선택한 방향은 **대화 중심 + 접이식 관제**다. 기본 화면은 단일 대화와 입력창이고, 현재 작업·하위 에이전트 목록을 필요할 때 펼친다. 항상 켜진 다중 패널 대시보드보다는 익숙한 CLI의 읽기 흐름을 우선한다.

첫 관제 범위는 현재 세션과 그 세션에서 런타임이 제공하는 하위 에이전트 상태다. 에이전트 선택 시 해당 활동 상세를 확인하고, 같은 화면에서 보거나 별도 터미널 창으로 열 수 있다. 다른 세션을 동시에 실행하거나 에이전트에 별도 지시를 보내는 기능은 후속 후보이며, 지원하는 런타임 동작을 확인한 뒤 범위를 정한다.

## 새 엔진의 책임

새 엔진의 책임은 터미널에서 읽고 조작하는 경험이다. 에이전트의 추론·도구 실행·권한 결정·컨텍스트 관리에는 관여하지 않는다.

| 부분 | 맡을 일 |
| --- | --- |
| 터미널 경계 | 입력 이벤트, resize, 터미널 모드 진입·복구 |
| 화면 모델 | 완료된 대화 기록, 갱신 중인 응답, 고정 입력 영역, 접이식 상세 |
| 렌더러 | 문자 셀 배치, 변경 영역 갱신, 커서 위치, 다시 그리기 |
| 텍스트 처리 | 한글·넓은 문자·결합 문자, 줄바꿈, 코드와 긴 줄 |
| 입력·포커스 | 여러 줄 편집, 붙여넣기, 읽기 모드, 상세·승인 화면의 키·클릭 처리 |
| 클릭 대상 | 셀 좌표와 선택 대상 연결, 포커스 이동, resize 후 클릭 영역 갱신 |
| 화면 갱신 | 스트리밍 이벤트 묶기, 입력 반응 유지, 읽던 위치 보존 |
| 코어 연결 | 런타임 이벤트를 UI 상태로 변환하고 사용자 동작을 요청으로 전달 |

개념 흐름: `Codex 런타임 ↔ 연결 계층 ↔ 대화·작업 상태 ↔ 새 Rust 화면 엔진 ↔ 터미널`.

엔진 자체는 메시지·목록·텍스트·상세 화면을 처리하고, 도구 실행·승인·usage의 의미는 앱 계층이 소유한다. 첫 구현에서는 모듈 경계로 분리하고 재사용 필요가 확인되면 독립 crate로 추출한다.

## 화면 동작 제안

- 기본 화면: 완료된 대화와 현재 응답, 작은 활동 요약, 여러 줄 입력창.
- 관제 열기: 현재 세션의 작업과 하위 에이전트를 목록으로 표시하고 활동 상세를 선택한다.
- 새 창 열기: 에이전트 항목의 명시적인 동작으로 해당 활동을 새 터미널에 연다. 자동으로 모든 에이전트의 창을 띄우지 않는다.
- 도구 상세 열기: 대화의 실행 요약에서 명령과 출력으로 이동한다.
- diff 열기: 변경 파일 목록에서 파일별 diff를 확인하고 닫으면 원래 읽던 위치로 돌아간다.
- 승인 도착: 승인 요청을 강조하되 입력 초안은 보존한다. 요청에 포커스를 옮긴 뒤 명시적으로 허용·거절한다.
- 에이전트 오류·완료: 활동 요약에 변화가 표시된다. 사용자가 읽고 있는 대화를 자동으로 교체하지 않는다.
- 좁은 창: 상세를 별도 화면으로 연다. 대화·입력 공간을 상시 패널로 줄이지 않는다.

기본 렌더링은 터미널의 대화 기록을 살리는 인라인 방식으로 제안한다. 관제·diff처럼 탐색이 필요한 화면은 전체 화면을 사용할 수 있다. 인라인에서는 복사·스크롤이 자연스럽지만 완료된 출력 수정에 제약이 있고, 전체 화면에서는 배치가 자유롭지만 복사·스크롤을 직접 다뤄야 한다. 두 방식의 전환과 상태 보존을 초기 기술 검증에서 확인한다.

## 클릭 조작

키보드와 클릭은 같은 사용자 동작으로 변환한다. 조작 방식에 따라 서로 다른 결과가 나오지 않게 한다.

| 대상 | 클릭 동작 | 키보드 동작 |
| --- | --- | --- |
| 도구 실행 요약 | 상세 펼치기·접기 | 선택 후 Enter |
| 변경 파일 | 파일 diff 열기 | 파일 선택 후 Enter |
| 에이전트 항목 | 활동 상세 선택 | 항목 이동 후 Enter |
| 에이전트의 새 창 버튼 | 별도 터미널 열기 | 같은 명시적 동작 실행 |
| 승인 버튼 | 표시된 범위 허용·거절 | 승인 영역에서 선택 후 실행 |
| 입력창 | 입력 포커스로 이동 | 입력 복귀 키 |

- 클릭 가능한 대상은 펼침 표시·버튼·선택 강조로 구분한다.
- mouse reporting을 사용할 수 없는 환경에서도 같은 작업을 키보드로 수행할 수 있다.
- 스크롤 휠, 텍스트 드래그 선택·복사, 터미널 고유 동작을 함께 검증한다. 우회 키를 모든 터미널에 동일하다고 가정하지 않는다.
- 클릭 좌표는 현재 렌더링된 화면의 셀 배치에 연결한다. 줄바꿈·resize 후 이전 클릭 영역은 폐기한다.
- 일반 터미널 scrollback으로 넘어간 과거 기록을 현재 화면처럼 클릭 가능한 것으로 취급하지 않는다. 과거 기록의 펼치기·접기는 앱이 소유하는 대화 탐색 화면에서 제공한다.

## 여러 터미널 창

사용 경험은 **메인 창에서 대화·관제, 보조 창에서 선택한 에이전트 상세**다. 별도 창은 같은 작업을 다른 곳에서 보는 클라이언트다.

### 역할

- 메인 창: 사용자 지시, 전체 작업·에이전트 상태, 승인 도착 알림, 새 창 열기.
- 에이전트 창: 선택한 에이전트의 대화·도구·변경·진행 상황. 처음에는 활동 열람부터 지원한다.
- 공용 런타임: 세션과 에이전트 실행을 유지하고 각 창에 상태를 전달한다. 실행 상태의 기준은 런타임이며, 읽던 위치·입력 초안·선택은 창별 상태다.
- 창 실행 어댑터: 선택한 터미널 앱에서 새 창을 열고 해당 런타임과 세션·에이전트 식별자로 연결한다. 터미널 앱별 실행 방식은 UI 엔진 바깥에 둔다.

제안 구조:

```text
메인 TUI ──────────┐
에이전트 A TUI ────┼── 공용 Codex app-server ── 세션 / 에이전트 실행
에이전트 B TUI ────┘
```

현재 소스에는 remote client와 별도 app-server daemon 기반이 있다. 이를 연결 후보로 사용한다. daemon은 실험적이며 여러 창 구독, 재연결, 승인 전달의 실제 동작을 검증해야 한다. 현재 기획은 작동을 보장하는 구현 결과가 아니다.

### 창과 작업의 수명

- 창 닫기는 기본적으로 화면 연결을 해제한다. 작업 중단은 별도 명시적 동작이다.
- 보조 창을 다시 열면 같은 실행에 연결하고 기록·현재 상태를 복구한다.
- 메인 창을 닫아도 공용 런타임을 유지하는 것을 목표로 한다. 모든 작업 종료와 런타임 종료는 별도 흐름으로 설계한다.
- 이미 열린 에이전트 창은 가능하면 활성화하고, 이를 지원하지 못하는 터미널에서는 다시 연결하는 선택을 제공한다.
- 새 창 실행 실패 시 현재 창의 상세 화면으로 접근할 수 있게 한다.

### 입력과 승인 소유권

- 첫 보조 창은 열람을 기본으로 한다. 에이전트에 별도 지시·중단을 보내는 권한은 런타임 규약을 확인한 뒤 제공한다.
- 승인 응답은 코어에서 요청을 전달받은 연결을 통해 처리한다. 임의의 창에서 모든 승인에 응답할 수 있다고 가정하지 않는다.
- 동일 요청을 여러 창에 표시하더라도 승인 처리 창을 하나로 정하고, 처리 결과를 나머지 화면에 반영한다. 중복 응답을 실행하지 않는다.
- 같은 에이전트에 여러 창이 지시할 수 있게 확장할 때는 입력 소유권 전환을 명시적으로 설계한다.
- 창을 늘리는 기능과 새 오케스트레이션 정책은 분리한다. 첫 단계는 기존 Codex 에이전트 실행을 여러 창으로 조작·관찰하는 UI이며, 새 스케줄러·handoff 정책은 후속 단계다.

## 공통 UX

첫 우선순위는 **조작감**이다: 키보드 탐색, 펼치기·접기, 승인, diff 검토. 조작 대상을 알 수 있고, 상세 화면에서 돌아왔을 때 원래 상태가 유지되어야 한다.

권장 상호작용 모델은 입력 모드와 탐색 모드를 구분하는 것이다. 입력 중에는 텍스트 편집을 우선하고, 탐색 중에는 대화 블록·도구·파일을 선택한다. 승인 요청 도착만으로 기존 입력 키를 승인 선택에 재해석하지 않는다. 승인 영역으로 명시적으로 이동한 뒤 허용·거절한다.

키 배치 초안: 탐색 진입과 상세 닫기는 Esc, 탐색 중 위·아래는 항목 이동, Enter는 선택 항목 상세 열기, Tab은 조작 영역 이동. Esc의 최종 동작과 실행 중단 키는 별도 확정한다. 글자 단축키는 탐색 모드에서만 고려한다.

### 대화와 진행 상태

- 사용자 지시, 응답, 도구 실행을 구분한다.
- 도구 출력은 실행 요약을 먼저 보이고 상세를 펼칠 수 있게 한다.
- 실행 중·승인 대기·중단 요청 중·중단 완료·오류·완료를 구분한다.
- 과거 내용을 읽는 동안 새 응답 때문에 읽는 위치가 바뀌지 않는다. 새 내용이 있음을 표시하고 최신 위치로 돌아갈 수 있게 한다.
- 스트리밍 중에도 입력 초안을 유지한다. 실행 중 제출 동작은 기존 Codex의 steer/queue 규약을 따른다.

### 입력과 탐색

- 여러 줄 입력, 붙여넣기, 파일 참조, 기존 slash 명령을 유지한다.
- 익숙한 CLI 조작을 기본으로 하고 화면에 현재 유효한 조작만 안내한다. 기존 단축키는 참고 자료이며 새 키 배치는 별도로 정한다.
- Enter/줄바꿈, 중단/닫기/종료의 키 배치는 기존 동작을 확인한 뒤 확정한다.
- 패널을 열고 닫아도 입력 초안과 대화의 읽던 위치를 보존한다.
- 한글 조합 입력, 넓은 문자, 코드 줄바꿈, 텍스트 선택·복사를 실제 터미널에서 확인한다.

### 승인과 변경 검토

- 승인 요청은 일반 로그보다 눈에 띄게 표시한다.
- 요청 종류, 명령 또는 파일, 실행 위치, 가능한 승인 범위를 표시한다.
- 코어가 제공하는 선택지만 노출하며 승인 범위를 UI가 임의로 넓히지 않는다.
- UI에서 중단을 눌렀다고 곧바로 중단 완료로 표시하지 않는다. 런타임 응답을 확인한다.
- 파일 변경은 제안된 변경, 적용된 변경, Git 작업 트리의 diff를 구분한다.
- 승인 여부와 diff 열람은 별도 동작이다.

### 상태 표시

- 기본 상태줄: 작업 폴더/브랜치, 모델, 현재 실행 상태.
- 사용량과 context 정보는 런타임이 제공하는 값만 표시한다. 제공되지 않는 비용을 추정해서 표시하지 않는다.
- 상세 usage는 별도 화면에서 열고, 상태줄의 밀도는 기획 과정에서 정한다.

## 첫 버전 범위

포함: 새 화면·입력 엔진, 키보드·클릭 조작, 세션 시작·재개, 대화 입력, 스트리밍, 도구 상태·상세, 승인, diff 열람, usage, 중단, 기본 오류 표시, 현재 세션의 하위 에이전트 상태 목록, 선택한 에이전트를 별도 터미널에 열고 재연결하기.

후속 후보: 여러 세션 동시 조작, 에이전트에 별도 지시, 테마 편집기, 고급 키 바인딩, 코어 교체, Jev/Decision, tier routing, 로컬 inference, UBIS, handoff.

## 구현 순서와 완료 기준

1. 원본 빌드와 실행을 확인하고 기준 동작을 기록한다.
2. 새 엔진의 최소 세로 흐름을 검증한다: 입력 → 예시 스트림 → 도구 요약 → 키보드·클릭으로 상세 열기·닫기 → resize → 종료. 이 단계는 실제 코어 연결의 완료 증거로 보지 않는다.
3. 실제 Codex 세션에 연결해 대화·입력·도구 상태를 구현한 뒤 승인·diff·usage·활동 목록을 붙인다.
4. 80×24와 120×40에서 입력, 대화, 승인 내용이 접근 가능한지 확인한다. 좁은 창에서는 상세를 전환 화면으로 표시한다.
5. 실제 세션의 시작·재개, 스트리밍, 중단, 승인 허용·거절, 변경 검토를 확인한다.
6. resize, 긴 도구 출력, 한글 입력, 복사, 오류 후 복구, 정상 종료 후 터미널 복구를 확인한다.
7. 메인 창과 보조 창을 같은 런타임에 연결해 활동·결과가 일치하는지 확인한다. 창 닫기·다시 열기에서 실행이 중복되지 않고 계속 진행되는지 확인한다.
8. 승인 처리 창과 다른 창의 동기화, 키보드·클릭의 동일 동작, 클릭과 선택·복사의 공존을 확인한다.
9. 새 엔진의 입력·포커스·상태 전이와 셀 단위 화면 출력을 검증하고 관련 기존 동작과 비교한다.

위 흐름이 실제 코어로 작동하면 첫 버전을 완료한다. 새로운 기능은 다음 단계로 넘긴다.

## 구현 반영 · 2026-10-01

독립 `custom-tui` crate를 만들고 설치된 Codex app-server에 연결했다. 현재는 화면 하단에 고정한 입력과 나머지 공간을 사용하는 대화, 같은 줄의 발신자 표시, 구분선으로 분리한 입력, 넓은 창의 작업 패널을 사용한다. 기본 UI는 무채색이며 선택 탭과 hover를 별도로 표시한다. `/` 명령 메뉴, 실제 스킬 목록과 입력, 모델 선택, 세션 목록과 재개, 완료된 턴의 클릭 분기, 언어·패널 설정을 추가했다. 화면은 앱이 소유하는 전체 화면이고 터미널 고유 scrollback을 쓰는 인라인 엔진은 아직 구현하지 않았다.
