# Native Core 실행 계약과 품질 기준

2026-10-03. 기준은 기획서의 “Core는 세계를 기억하고, Worker는 문제를 푼다”와
Codex 대비 작업 품질 유지다. TUI 렌더링과 도구 노출 수는 작업 능력의 대리 지표가 아니다.

2026-10-04에는 그래프 후보를 실제 Core 배분·회수·병합 경로에 연결했다. 기존
코드의 독립된 2–4개 쓰기 범위에 한정하며, 범용 요청 기획기나 Codex 동급 품질을
완성한 것은 아니다. 부모·자식 공통 호출 한도와 비용 집계, 자식 기록 복원,
공급자 오류 코드 보존, 정확한 EndTurn 완료 JSON의 제안 정규화를 추가했다.
정규화된 제안도 실제 patch의 독립 검증과 승인을 통과해야 한다.
[실제 세션 감사·실모델 실패·남은 한계](loom-agent-session-audit-2026-10-04.md)를 참고한다.

## 재현한 결함과 수정

대화 압축은 최근 메시지의 짧은 조각만 연결했다. 먼저 찾은 원인 위치는 뒤에
무관한 파일을 읽으면 사라졌다. artifact는 있었지만 다음 판단에 쓰는 상태가 없었다.
`compaction_preserves_early_source_evidence_and_the_active_plan`이 변경 전 실패하고
변경 후 통과했다.

Worker의 finish 뒤 Core 검증이 실패해도 자동으로 수리하지 않았다. Worker의
제안 종료와 Core의 acceptance를 분리한다는 기획에 어긋났다.
`core_repairs_a_finished_proposal_from_validation_evidence_without_user_resume`으로
실패한 제안 → 복원 → 수정 → 독립 검증 → 적용을 확인했다.

- WorkMemory가 질의, 관측 결과, 실패, 원문 artifact를 대화 밖에 보관한다.
  WorkerResult에 저장하고 다음 시도에 전달한다. 모델에는 예산 안에서 실패·수정·
  검색 위치를 우선한 projection과 원문 참조를 제공한다. 전체 인덱스를 복사하지 않는다.
- 활성 계획은 모델의 제안, 도구 결과는 Core의 관측이다. 모델이 completed를
  선언해도 성공 판정이 되지 않는다.
- 변경 가능한 동작과 Worker 교체 뒤에는 이전 관측을 possibly stale로 표시한다.
  현재는 보수적으로 전체 관측의 epoch를 바꾼다. 파일별 digest에 의한 선택적
  무효화와 세션 간 검색은 아직 구현하지 않았다.
- 실제 patch의 Core 검증이 실패하면 남은 시도·시간·토큰 예산 안에서 복원하고
  수리한다. 동일 실패 patch의 재제출은 빌드와 재시도를 반복하지 않는다.
- 취소, 명시적 unresolved, 무변경 답변, 승인 대기의 종료 의미는 유지한다.
  검증 명령 미지정, sandbox 거부, 검증 시간 초과는 코드 수리 대상으로 돌리지 않는다.
  max_attempts=1은 자동 수리 없이 실패를 보존한다.
- 예전 WorkerResult에 WorkMemory가 없어도 default로 읽을 수 있다.

## 진행과 중단 보고

Core가 모델 요청 시작, 도구 실행 시작, 완료 결과, 단계별 진행을 기록한다.
진행 보고는 모델에게 추가 설명을 요청하지 않고 관측된 결과에서 만든다. 같은 도구를
한 응답에서 여러 번 실행하거나 Worker를 교체해도 operation_id가 달라 결과가 덮이지
않는다. Native 화면의 접힌 도구에는 대상과 결과 요약이 보이며, 좁으면 결과를 다음
줄에 표시한다. CLI는 일반 모드에서 진행을 stderr로 출력하고 JSON 출력 계약은 유지한다.

한도에 가까워지면 Worker에게 넓은 탐색을 멈추고 현재 근거로 수정·검증 또는 정확한
미완료 설명을 마무리하도록 한 번 안내한다. 기존 시간·토큰 상한을 풀지 않는다.
수정 작업에는 전체 실행 시간의 10%(최대 30초)를 독립 검증에 남긴다. 다음 Worker를
시작할 때도 같은 예약 시간을 지키며, 예약 시간만 남았다면 새 시도를 하지 않는다.

미완료, 검증 실패, 범위 충돌, 취소 때 Core가 로컬 중단 보고를 저장한다. 최근 수행한
도구, 격리 사본의 실제 patch 파일, 모든 시도의 모델 요청·토큰·모델 대기 합계,
모델 실패 원인, Core 검증, 원본 반영 여부, 미완료 계획과 trace 참조를 포함한다.
보고 생성에 모델 호출을 쓰지 않아 공급자 실패나 남은 예산 0에서도 보고를 만들 수 있다.
마지막 재시도의 대기 시간이 0이라도 앞선 호출의 지연이 누적 보고에서 사라지지 않는다.
도구 완료와 모델의 성공 선언을 Core 검증 통과로 취급하지 않는다.

호출 한도 뒤 부분 수정, 수정 직후 취소, 마지막 호출의 공급자 시간 초과, 재시도
합산, 검증 시간 예약, 동일 도구의 배치 호출을 회귀 테스트로 확인했다. 실제 CLI 출력은
[`core-stop-report-2026-10-03.json`](../loom-core/measurements/core-stop-report-2026-10-03.json)에
보존했다. PTY 검사도 Native에서 두 read 결과와 공급자 실패 보고가 80·40열에서 보이는지
검증한다.

Gemini 3.8 Flash로 average-empty 과제를 실행했으나 파일 조회 이후 다음 호출이
시간 초과로 끝났고, 재시도는 gateway cooldown에 막혔다. 완수·숨은 테스트는 실패했다.
이 실행에서 마지막 시도만 요약하던 결함을 발견해 누적 보고와 검증 시간 예약을
보완했다. 당시 실모델 결과는
[`core-stop-report-live-2026-10-03.json`](../loom-core/measurements/core-stop-report-live-2026-10-03.json)에
보존했으며, 이 결과를 완수율 개선의 증거로 사용하지 않는다.

### 일반 질문을 편집 실패로 표시한 전달 결함

사용자의 “너에게 주어진 도구가 뭔지 말해봐”에 모델은 답했지만,
NativeBackend가 ExecutionOptions의 Auto를 Edit로 강제 변환했다.
Core는 전달된 Edit 계약에 따라 실제 patch가 없으므로 실패 보고를 생성했다.
도구를 더 실행해야 하는 문제가 아니라 요청 모드 전달이 잘못된 사례다.

Native는 이제 Auto를 그대로 전달한다. 추가 분류 모델 호출이나 질문 키워드
목록을 넣지 않는다. :edit 및 명시적으로 설정한 Edit는 patch를 요구하고,
실제 수정안의 독립 검증·승인·원본 반영 조건도 유지한다. :inspect와 :chat은
기존 명시적 모드로 남는다. Auto의 답변 수락은 완전한 의미 기반 요청 분류나
자연어 편집 요청의 완료 조건 검증을 구현했다는 뜻은 아니다.

기존 Native 테스트의 “모든 기본 입력은 편집” 가정은 이 결함을 고정하고 있었다.
편집 patch 요구 테스트와 inspect 이후 편집 테스트는 :edit 입력으로 바꾸고
실패 판정 assertion을 유지했다. 일반 도구 질문은 원문 그대로 별도 회귀 테스트를
추가해, 한 번의 응답·정상 완료·실패 보고 없음·세션 보존을 확인했다.
화면 안내 검사도 변경 전 실패, 변경 후 통과했다. 최종 클라이언트 212개·
self-check 434개와 PTY의 일반 질문·편집 검증/승인/반영·중단 보고·Esc가 통과했다.
사용자 기록의 모델 대기 44초는 이 수정에서 해결했다고 주장하지 않는다.

## Codex급이라고 판정하기 위한 조건

이번 메모리와 검증 수리 루프는 필요한 구성 요소다. 작업 의도 해석, 의존 관계를
가진 계획의 검증, 모델별 완수 능력에 따른 routing, 큰 저장소의 근거 선택은
여전히 별도 검증이 필요하다. lexical graph anchor는 후보이며 계획의 정답이 아니다.
기존 테스트 통과만으로 요청한 기능이 완성됐다고 판단하지 않는다.

| 영역 | 합격 기준 |
| --- | --- |
| 작업 완수 | 동일 base·요청·독립 숨은 테스트로 Native와 Codex 비교. 실제 patch·회귀·요청 제약을 함께 채점 |
| Core 효율 | 동일 실제 served model로 변경 전후 비교. 완료율을 유지하면서 uncached input·재탐색·호출 감소 |
| 계획 | 결과·완료 조건을 구조화하고 Core가 검증. 조사·구현·검증의 의존 결과를 연결. 계획문 자체는 성과가 아님 |
| 승격 | 요청 tier가 아닌 실제 모델과 완수 결과를 기록. 같은 약한 모델 재선택은 승격 성공이 아님 |
| 병렬 | Single 대비 중복 맥락·검증 비용까지 포함해 이득이 확인될 때 채택 |
| 자기개선 | revision과 성공 조건이 고정된 실제 실패 과제 사용. 채점 기준은 일꾼의 수정 범위 밖에 두고 미사용 과제에서 회귀 확인 |

모델 간 능력 차이를 Core 최적화 효과로 계산하지 않는다. Codex와 Native 비교는
제품 품질 비교이며 동일 모델을 보장할 수 없으면 그 조건을 명시한다.

## 2026-10-04 작업 루프 보완

실제 Groq OSS 120B 실행에서 반복 조회, 존재하지 않는 도구 요청, 잘못된 정규식이
관측됐다. 변경 전 average-empty는 원본 수정 없이 실패했다. 다음 결함을 재현한 뒤
Core에서 수정했다.

- 도구와 각 검증 명령은 Worker의 남은 시간만 사용한다. 모델 대기 뒤 명령을
  시작하거나 여러 검증 명령을 실행해도 최초 시간 한도를 다시 받지 않는다.
  시간 종료 뒤 재시도 대기와 자식 작업 기다림도 같은 종료·취소 신호를 확인한다.
- 명령의 0 이외 종료 코드는 실패다. 종료 코드와 출력 요약을 진행 기록에 남긴다.
  큰 PTY 출력은 output 필드만 줄여 유효한 JSON을 보존하고 원문 artifact는 유지한다.
- rg 종료 코드 2를 “검색 결과 없음”으로 숨기지 않는다. 정규식·경로 오류와
  literal=true 재시도 안내를 모델에 전달한다.
- Core가 단일 파일을 수정하면 다른 파일의 read/outline 근거는 재사용한다.
  경로·inode로 symlink와 hardlink 별칭을 함께 무효화한다. 전체 검색, 외부 명령,
  변경 범위를 모르는 동작은 보수적으로 무효화한다. 실행 중인 터미널이 있으면
  결과를 재사용하지 않는다. 별도 도구 호출 없이 파일이 바뀌는 회귀 사례도 확인했다.
  Unix 외 환경은 파일별 재사용을 적용하지 않는다.
- 두 번 연속 새 근거가 없는 호출 뒤 한 번 수정·검증 또는 정확한 미완료 설명을
  요구한다. 세 번째 반복은 기존처럼 중단한다. 같은 잘못된 도구 요청의 반복도
  집계한다. 교정은 추가 시간·호출 한도를 부여하지 않는다.
- 공급자가 생성된 도구를 거부한 명시적 tool_use_failed 오류만 한 번 교정한다.
  실행되지 않은 호출을 수행 기록으로 만들거나 모델이 만든 이름을 실행하지 않는다.
  일반 BadRequest와 반복되는 생성 오류는 실패를 보존한다.
  Router도 이 오류를 도구 미지원으로 기억하거나 다른 모델로 넘기지 않는다.
  오류를 Worker에게 전달하고 같은 모델을 다음 교정 호출에 사용할 수 있게 유지한다.
  실제 도구 미지원 모델을 제외하는 기존 판정은 유지한다.

변경 없는 helper.rs의 반복 조회는 회귀 과제에서 10,120 → 237바이트였다.
이는 도구 결과 바이트 측정이며 실제 모델의 토큰 절감률을 뜻하지 않는다.

같은 Groq 모델·average-empty·16단계·총 90초 조건으로 다시 실행했다. 첫 후보는
함수를 수정한 뒤 공급자의 도구 생성 오류에서 종료했다. 교정 경로를 추가한 후보는
함수와 호출부를 수정했지만 마지막 호출 시간 초과로 Native 완수·원본 적용은 실패했다.
trace의 성공한 두 edit를 별도 사본에 복원해 숨은 테스트 3개가 통과하는지는 확인했다.
이 보조 채점은 Native 벤치 통과로 계산하지 않는다. 자동 마무리와 검증까지 연결되지
않는 문제가 남았으며, 실제 완수율·속도·토큰 효율 개선을 주장하지 않는다.
Router 교정까지 반영한 마지막 동일 조건 실행도 14회 호출 뒤 시간 초과로 실패했다.
최종 Core 222개·클라이언트 211개 테스트와 clippy, self-check 433개, release 빌드가
통과했다. 최종 release의 Native 승인·반영, 작업 결과·중단 보고, 종료·Esc 중단은
실제 PTY에서 확인했다.

조건·회귀 검증·실모델 결과는
[`worker-loop-2026-10-04.json`](../loom-core/measurements/worker-loop-2026-10-04.json),
별도 수정안 채점은
[`worker-loop-isolated-grade-2026-10-04.json`](../loom-core/measurements/worker-loop-isolated-grade-2026-10-04.json)에
기록한다. WorkMemory 전체 epoch 무효화 정책은 기존과 같다. 이번 변경은 Worker의
중복 조회 캐시에 대한 파일별 재사용이며, 전역 메모리의 파일별 버전 관리와는 별개다.

## 실모델 비교

expr-precedence, token-bucket을 같은 Gemini 3.8 Flash 경로, jobs=1,
task timeout=180초로 실행했다. 변경 전후 모두 0/2였으며 후속 호출에서 gateway
read timeout과 cooldown이 발생했다. Sonnet 4.6은 live catalog 거부,
Sonnet 5.5는 첫 호출 응답 시간 초과로 정상 비교를 하지 못했다.
