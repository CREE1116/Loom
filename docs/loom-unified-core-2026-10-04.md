# V2 자산을 연결한 V3 작업 루프

이 변경은 V3에 V2의 심볼 추출·참조 그래프·캐시를 연결하고, 자연어 계획과 실제
실행 판정을 분리한다. V1/V2 저장 상태와 기존 명시적 편집 경로는 유지한다.
Codex와의 동등 성능이나 모든 과제의 완료를 입증한 결과는 아니다.

## 판단 경계

- 일반 자연어 요청은 모델이 `plan_work`로 의도, 작업 단위, 읽기/쓰기 범위, 의존성,
  도구 호출과 결과 조건을 제안한다. 요청의 “만들”, “지워”, “삭제” 또는 영문 동작
  단어를 검사하지 않는다. 임시파일 전용 실행기나 세미콜론에 따른 작업 분할도 없다.
- `:edit`, `:inspect`, `:chat`, `/list .` 등은 명시적인 명령 문법이다. 파일명/심볼명
  검색은 소스 맥락 조회에만 사용하며 요청 의도를 결정하지 않는다. 자연어
  `list the tools available`도 자동 디렉토리 명령으로 취급하지 않는다. 기존 `list .`
  문법은 `:inspect list .` 또는 CLI `--intent inspect` 안에서만 명시적 명령으로 쓴다.
- 작업 계획은 실행 전에 원래 요청과 별도로 비교한다. 검토 모델은 누락된 범위나 순서를
  발견하면 전체 계획을 교체한다. `Answer`와 조건·의존성이 없는 단일 Semantic 읽기 전용
  조사 계획은 이 실행 검토를 생략한다. 여러 워커·수정·절차 계획의 검토는 유지한다. 검토 실패는
  도구 실행 전에 보고한다. 검토에는 사용 가능한 모델 중 강한 등급을 우선한다.
  강한 모델이 없으면 작은 모델이나 로컬 모델로 검토하며, 실제 모델을 원장에 남긴다.
- Core는 경로, 권한, 등록 도구의 필수 인수와 기본 타입, 순환 의존성, 파일 충돌,
  실제 도구 결과와 파일 후조건을 검사한다. 모델의 성공 선언으로 검증을 대체하지 않는다.
- 정확한 인수가 이미 있는 작업은 모델 없이 실행한다. 의미적 탐색/수정은 워커가
  맡는다. 수정 결과는 Core가 격리 사본에서 검증한다.
- 영구 변경은 실제 patch와 객관적 검증이 필요하다. 생성→수정→확인→삭제처럼
  순변경이 없는 절차는 실행 기록과 후조건을 통과하면 완료할 수 있다. 원본에서
  임시 동작을 실행하는 것이 아니라 격리 사본에서 실행한 결과다.

## 모듈과 재사용

| 위치 | 책임 |
| --- | --- |
| `control/coordinator.rs` | 모델의 자연어 해석, 계획 제안, 별도 문맥의 범위 검토 |
| `control/protocol.rs` | 공급자용 평면 프로토콜 → 내부 타입 변환 |
| `control/plan.rs` | 작업 DAG, 파일 범위, 그래프 참조 보강, 충돌 직렬화 |
| `control/dispatch.rs` | 최대 4개 독립 워커 실행, 의존 결과 전달, patch 병합 |
| `control/planned.rs` | 계획→실행→검증→승인 생명주기 |
| `world/graph.rs` + V2 `graph/extract` | 여러 언어의 심볼, 전체 함수 범위, 참조와 추출 캐시 |
| `worker/registry.rs` | `Tool` 등록, 효과·권한·인수 검증 |
| `worker/memory.rs` | 최근 완전한 도구 교환 2개와 제한된 관측/파일 맥락 |
| `worker/events.rs` | 워커 식별자, 발화, 도구 성공/실패, 전체 요청·응답 trace |
| TUI `version_conversation.rs` | 여러 워커를 하나의 답변과 접힌 작업 기록으로 투영 |

새 도구는 `Tool` 구현을 `Core::with_tool`로 등록한다. 모델 프로토콜과 실행기는
같은 Registry에서 기능 목록을 얻는다. 공급자는 `ModelPort`, 검증기는 `Validator`
경계를 사용한다. 복구된 커스텀 도구 계획의 승인에도 같은 도구를 다시 등록해야 한다.
기본 인수 검사보다 복잡한 도구별 제약은 해당 구현이 검증한다.

## 중단과 증거

계획·검토·워커의 모델 호출/토큰은 공유 상한에 포함된다. 같은 인수로 같은 파일 상태에서
3회 반복하면 전체 한도를 소진하기 전에 중단한다. 도구 실패 후 같은 응답에 든
`finish`는 수락하지 않는다. 공급자 장애를 코드 수정 재시도로 반복하지 않는다.
시간/호출 제한은 무한 실행 방지를 위해 유지한다. 모든 과제의 완료를 보장하지 않는다.

Core의 `.loom-v3/events.jsonl`에는 전체 계획, 모델 요청/응답, 도구 인수/결과가 남는다.
TUI에서는 하나의 대화에 모델 발화와 결과를 표시하고 도구 기록을 접는다. 실패한
도구를 성공 표시하지 않는다. 재시작/승인 이후에도 관측과 작업 기록을 복원한다.
검증 명령은 파일 후조건의 표시 문자열과 분리해 저장한다. 결정적 계획은 승인 때
다시 실행하고 후조건과 정확한 diff를 확인한다. 원본 revision 변경 시 적용을 거절한다.

## 검증과 실제 모델 관측

회귀 검사는 자연어 동작 단어가 포함된 설명 요청, 단어 없는 절차 요청, 순변경 없는
완료, 실패 후조건, 필수 인수 누락, 읽기 전용 권한, 승인 복구, 실제 병렬 워커 및
그래프 참조에 따른 직렬화, 실행 전 계획 수정, 검토 경로의 모델 분리를 포함한다.
최종 회귀 검사는 V3 39개, TUI 225개가 통과했고 화면 자체 검사 442개도 통과했다.
release 바이너리의 PTY에서 워커 2개/모델 호출 2회/도구 6회와
후조건 4개의 실행, 접힌 로그와 재시작 복구를 확인했다. 의존 워커가
원본의 오래된 문맥을 받는 실패도 재현하고, 병합된 소스와 갱신한 AST 범위에서
문맥을 만들도록 수정했다. 갱신에는 원래 작업 저장소의 추출 캐시를 재사용한다. fixture 성능을 모델 벤치로
간주하지 않는다.

범위 검토를 추가하기 전, 실제 Gemini Pro 경로에서 두 파일명을 명시한
동일한 생성·수정·읽기·삭제 요청을 실행했다. 초기 계획
스키마의 중첩 선택지가 게이트웨이 경로에서 첫 선택지만 사용하게 되는 문제가
관측됐다. 모델이 “delete_file만 허용된다”고 응답했다. 전송 형식을 평면화하고
내부 검증 타입을 유지한 뒤, 모델 호출 1회로 도구 8회와 후조건 8개를 통과했다.
약 21.179초, 보고된 입력 1,364 / 출력 2,810 토큰이었다. 모델은
`omniroute/agy/gemini-3.1-pro-high`, effort `low`, 출력 상한 8,192였다.
출력 상한 4,096의 초기 시도에는 추론이 상한을 소진해 빈 응답(`MaxTokens`)도 있었다.
같은 요청을 `omniroute/gemini/gemini-3.1-flash-lite`에서도 실행해 모델 호출 1회,
도구 9회, 후조건 8개를 통과했다. 약 3.358초, 입력 1,289 / 출력 750 토큰이었다.
두 초기 성공 실행의 도구 인수와 각 파일의 실제 beta 읽기 결과도 별도로 확인했다.
이 숫자는 검토 단계가 없는 이전 실행 관측이며 최종 경로 비용으로 쓰지 않는다.

원래 요청인 “이곳저곳에 임시파일 만들어서 수정도해보고 삭제도해봐”에서는
Flash Lite가 한 파일로 범위를 줄이고도 Core 후조건을 통과했다. 같은 모델의
별도 문맥 검토도 이를 놓쳤다. 검토가 선택된 작업 모델에 고정되던 어댑터를
수정하고 Pro High 검토 경로를 지정한 최종 실행은 단일 파일 초안을 두 파일로
교체했다. 계획/검토 2회, 도구 6회, 후조건 6개, 약 22.467초, 입력 2,883 / 출력
2,825 토큰이었다. 도구를 위한 추가 모델 호출은 없었다. 다만 두 파일이 모두
루트에 있었으므로 여러 디렉토리를 요구하는 엄격한 범위 판정은 **실패**로
보존했다. Core의 Accepted와 요청 전체의 의미적 성공을 같은 것으로 취급하지 않는다.

`--model`은 작업 모델을 유지한다. `--core-review-model auto`는 사용 가능한
모델 중 도구·비용·문맥·가용성 조건을 만족하는 가장 강한 등급을 우선하며
별도 모델/역할을 원장에 기록한다. Flagship이 없어도 실행할 수 있다.
`--core-review-model MODEL`로 검토 모델을 명시할 수 있다. 저렴한 모델이나
로컬 모델도 명시적으로 지정할 수 있지만 위 관측처럼 범위 판단 품질은 보장하지 않는다.
실패한 초기 실행까지 포함한 [원시 관측](../bench/results/loom-unified-smoke-2026-10-04.json)을
보존한다. 이 단일 요청 관측은 복잡한 코딩 과제 또는 정밀 속도 벤치의 근거가 아니다.

## 한계

그래프 참조는 이름 기반 근사라 정확한 타입 해석이 아니며 보수적으로 직렬화할 수
있다. 작업 단위의 의미적 완전성과 후조건 선정은 여전히 모델 판단에 의존한다.
모든 동적 읽기가 선언된 범위에 갇힌다고 보장하지 않는다. 실제 쓰기 범위와 병합은
검사하지만 동적 의존성을 완전히 증명하는 시스템은 아니다. 명시적 `:edit` 경로는
기존 단일 워커와 복구 루프를 유지하며 자동 계획 경로와 비용이 다르다.
전체 대형 과제 벤치, 로컬 모델 성능, 자율 실패 분석→수정→기준선 평가의 자동 승격은
이 변경으로 완성됐다고 주장하지 않는다.

```sh
scripts/loom --backend v3 --model MODEL
# 공유 공급자 어댑터를 통한 자연어 계획의 headless 검증
custom-tui/target/release/custom-tui --bench-core v3 --core-intent auto \
  --cwd REPO --model MODEL --core-review-model REVIEW_MODEL --run '요청' --no-approve
```

실행 중인 TUI는 다시 빌드한 코드를 즉시 읽지 않는다. Ctrl+Q 후 재시작해야 한다.
