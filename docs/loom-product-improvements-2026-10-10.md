# Loom 사용성·엔진·도구·스킬 개선 기획

2026-10-10. 저장소 구현과 공식 공개 자료를 비교한 개선안이다.
완료 표시가 없는 항목은 계획이며, 목표 수치는 측정 결과가 아니다.

## 제품 방향

Loom의 강점은 격리된 변경 제안, AST 근거, 원격·로컬 혼합 모델이다.
이를 유지하면서 사용자가 명령을 외우는 시간, 모델이 탐색에 쓰는 왕복,
실행 상태를 이해하기 위해 로그를 뒤지는 시간을 줄인다.
기능 개수보다 **요청 → 대상 지정 → 조사 → 변경 → 확인 → 재개** 흐름을 기준으로 판단한다.

## 이번에 반영한 개선

### 1. 명령을 외우지 않아도 되는 검색 메뉴

`Ctrl+P` 또는 기존 메뉴 버튼으로 열고 이름·설명으로 검색한다.
예: “컨텍스트”를 입력하면 압축과 컨텍스트 확인 명령을 찾을 수 있다.
검색 문구는 대화 초안과 별개로 보관한다. Enter는 선택한 동작을 실행하고,
인자가 필요한 명령은 입력란에 완성한다. Esc는 초안과 커서·선택을 보존한다.
실행 중 Esc의 중단 우선순위, 질문·승인의 입력 소유권을 유지한다.
결과가 없을 때 Enter로 대화가 잘못 전송되지 않는다.

완료 조건: 좁은 화면과 넓은 화면의 검색·선택·클릭 경로, 초안 보존,
인자 입력 취소, 빈 검색 결과, 검색 커서가 화면 검사와 회귀 검사로 확인된다.

### 2. 파일 탐색과 내용 검색의 도구 개선

- `glob`: `**/*.rs`, `**/tests/**` 같은 패턴으로 파일을 찾는다. 경로 범위,
  결과 상한, 정렬, ripgrep의 ignore·glob 우선순위, 불완전한 결과 표시를 지원한다.
  명시한 glob은 ripgrep 규칙에 따라 ignore 항목보다 우선할 수 있다.
- `find`: `include` 파일 패턴, `case_sensitive`, `limit`를 추가한다.
  결과가 많아도 첫 코드 근거를 보여주고 범위가 불완전함을 표시한다.
  단일 파일 검색도 파일명·줄번호가 남는다.
- 검색 프로세스는 기존 취소 가능한 프로세스 경계를 재사용하고 작업의 남은
  제한 시간이 지나면 프로세스를 종료·회수한다. 출력을
  디스크에 받으며 각 스트림의 메모리 미리보기는 128 KiB 이내로 제한한다.
  이 상한은 전체 프로세스 메모리나 검색 시간의 상한이 아니다. 결과 스풀은
  임시 파일이며 작업 기록으로 보존되는 artifact와 구분한다.
- `glob`는 기본 도구군에 넣어 별도의 도구 활성화 호출 없이 사용할 수 있다.
  읽기 전용 작업과 하위 워커의 파일 소유권 경계에서도 읽기 도구로 취급한다.

예: `glob {"pattern":"**/*test*.rs","path":"loom-core"}`로 대상을 찾고,
`find {"pattern":"cancel","include":"*.rs","case_sensitive":false,"limit":20}`로 좁힌다.
이미 알려진 파일 범위는 기존 `read_many`로 묶어 읽는다.

완료 조건: 파일 패턴·범위·잘못된 입력·잘림 표시, 읽기 전용 워커의
실제 도구 호출, 큰 stdout/stderr의 메모리 미리보기 제한을 확인한다.

### 3. LMX 대기 취소와 완료 경계

모델 슬롯 대기를 짧은 간격으로 확인해 취소된 요청이 나중에 모델을
로드하지 않게 한다. 대기·로드 앞뒤, 마지막 스트리밍 콜백 뒤에도 요청
상태를 확인한다. 동기 네이티브 로드·평가 자체의 강제 중단은 구현하지 않는다.
진행이 있을 때 다시 시작하는 기존 추론 stall timeout 의미는 유지한다.

완료 조건: 실제 모델이 없어도 독립 mutex를 사용한 대기 취소·대기 시간
초과·즉시 획득과 콜백 취소 회귀 검사가 실행된다.

### 4. 실제 작업을 위한 기본 스킬

`loom-plan`, `loom-debug`, `loom-review`를 번들에 추가한다.
계획에는 완료 조건·범위·검증을, 디버그에는 재현·원인 분리·재검증을,
리뷰에는 구체적 트리거와 파일 위치가 있는 문제를 요구한다.
사용자의 요청 범위와 현재 도구의 실행 권한에 맞춰 동작한다.
계획만 요청했을 때 편집하지 않으며, 구현을 요청했을 때 별도 승인 게이트를
추가하지 않는다. 실행하지 않은 검사를 통과했다고 쓰지 않는다.

완료 조건: 배포 바이너리에 포함, 설치와 업데이트, 사용자가 수정한 사본
보존, frontmatter 검증. 스킬의 실제 모델 품질 개선은 아래 벤치마크로 별도 평가한다.

## 성능과 품질 측정

### 도구 왕복과 문맥

같은 고정 revision의 작은 저장소와 큰 저장소에서 다음을 비교한다.
파일 찾기, 특정 언어 검색, 같은 이름의 심볼 구분, 실패 로그 조사,
두 파일 변경을 대표 작업으로 고정한다. 기존/개선 도구 각각 동일 모델과
설정으로 실행해 성공률, 도구 호출 수, 입력·출력 토큰, 도구 출력 bytes,
검색 지연과 최대 메모리를 기록한다. 캐시가 없는 실행과 재사용 실행은 분리한다.
연속 워커에서 비동기 작업 폴더 정리 때문에 실행 슬롯이 바뀌는 경우도 기록해,
같은 슬롯의 AST 캐시 재사용과 사용자 작업 전체의 재사용률을 구분한다.
이번 미리보기 제한은 회귀 검사로 증명하지만 전체 처리 속도 개선율은 주장하지 않는다.

### 엔진 첫 응답과 메모리

단순 tokens/s 외에 cold/warm 첫 가시 텍스트 시간, 모델 대기·로드·prefix
복원·prefill·decode 시간, 취소 지연, peak 메모리를 기록한다.
모델 연속 선택과 8K/16K 컨텍스트 경계를 별도 시나리오로 둔다.
GGUF 컨텍스트 성장 때 token cache를 비우는 현재 동작을 기준선으로 측정한 후,
백엔드 state transfer 지원과 일시 메모리 비용을 확인해 보존 방식을 설계한다.
native kernel·양자화·expert 배치를 근거 없는 추정으로 바꾸지 않는다.

### 스킬

애매한 기능 요청, 재현 가능한 버그, 실제 결함이 있는 diff, 결함이 없는
diff를 고정 fixture로 만든다. 스킬 유무를 비교해 재작업, 오탐 리뷰,
잘못된 완료 주장, 불필요한 도구 호출을 기록한다. frontmatter 통과와
스킬 문장 존재만으로 모델의 작업 품질이 개선됐다고 판단하지 않는다.

## 검증 기록

2026-10-10, macOS에서 다음을 확인했다.

| 검사 | 결과 |
| --- | --- |
| `cargo test --manifest-path loom-core/Cargo.toml -- --test-threads=1` | 468 통과, 0 실패, 기존 25 ignored |
| `cargo test --manifest-path loom-tui/Cargo.toml -- --test-threads=1` | 320 통과, 0 실패, 기존 3 ignored |
| `cargo build --manifest-path loom-tui/Cargo.toml` | 성공 |
| `cargo run --manifest-path loom-tui/Cargo.toml -- --self-check` | 845 검사, 0 실패. 검색·초안·커서·빈 결과를 폭 48/100/180에서 확인 |
| 새 스킬 frontmatter 검증 | 3개 모두 통과 |
| `git diff --check` | 통과 |

캐시 재사용 검사는 백그라운드 작업 폴더 정리가 끝난 뒤 같은 슬롯을
재사용하도록 동기화했다. 캐시 객체의 동일성과 변경 파일만 재파싱하는
