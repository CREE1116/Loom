# 코어의 속도·토큰·난도 분해·저비용 모델 평가

2026-10-04. 정답률만으로 코어를 비교하지 않고, 공개 검증과 승인 재검증까지의 시간,
입력+출력 토큰, 실패한 시도의 소비, 실제 워커 분할, 작은 모델의 실행 가능성을 측정했다.
평가는 실행 전에 고정한 숨은 테스트로 한다. 모델이 완료라고 말하거나 빌드만 통과해도
정답으로 채점하지 않는다. 세 코어 모두 승인 전 원본 보존을 검사한다.

## 가장 분명한 관측

**Flash-lite에서 추가 완료 호출을 Core 검증 전달로 바꾸면 전체 토큰이 줄었다.
파일별 병렬 분할은 같은 검증 전달 방식의 단일 워커보다 경제적이지 않았다.**
이 결과는 두 종류의 작은 독립 과제에 한정된다. 큰 작업에서도 분할이 불리하다는 뜻은 아니다.

두 기능 및 네 기능 과제를 각각 3회, 같은 모델로 실행했다. 모든 방식이 숨은 테스트 6/6을 통과했다.
`handoff`는 실제 편집을 받은 뒤 별도 모델 완료 호출을 기다리지 않고 Core가 검증하는 **실험 모드**다.
쓰기가 일어났다는 사실을 의미적 정답으로 간주하지 않으며 원본 반영은 별도 승인이 필요하다.

| V2 방식 | 통과 | 모델 요청 합계 | 전체 입력+출력 토큰 | 승인 재검증 포함 시간 중앙값 |
| --- | ---: | ---: | ---: | ---: |
| 기존 단일 워커 | 6/6 | 12 | 30,724 | 10.078초 |
| 단일 워커 + Core 검증 전달 | 6/6 | 6 | 16,734 | 9.915초 |
| 분할 워커 + 같은 검증 전달 | 6/6 | 18 | 29,819 | 10.125초 |

검증 전달은 이 표에서 토큰을 **45.5%**, 모델 요청을 50% 줄였다. 그러나 모델 대기 합계는
40.838초 → 41.051초로 거의 같았다. 호출 수가 줄었다고 속도 향상을 보장하지는 않는다.
입력은 줄고 출력은 늘었으므로 입력 토큰만 보고 절감률을 계산하면 과장된다.

과제별 중앙값이다. 전체 토큰 중앙값은 입력 중앙값+출력 중앙값을 더해서 만든 값이 아니다.

| 과제 | 방식 | 모델 요청/실행 | 전체 토큰/실행 중앙값 | 재검증 포함 시간 중앙값 |
| --- | --- | ---: | ---: | ---: |
| 독립 기능 2개 | 기존 단일 | 2 | 4,177 | 9.803초 |
| 독립 기능 2개 | 단일 + 검증 전달 | 1 | 2,516 | 8.761초 |
| 독립 기능 2개 | 2개 워커 + 검증 전달 | 2 | 3,131 | 9.445초 |
| 독립 기능 4개 | 기존 단일 | 2 | 5,888 | 10.353초 |
| 독립 기능 4개 | 단일 + 검증 전달 | 1 | 3,606 | 11.314초 |
| 독립 기능 4개 | 4개 워커 + 검증 전달 | 4 | 6,740 | 10.804초 |

같은 반복 번호의 단일+전달과 분할+전달을 짝지어 비율을 계산하면, 분할/단일의
시간 비율 중앙값은 2개 과제 1.249, 4개 과제 1.216이었다. 토큰 비율 중앙값은 각각
1.453, 2.031이었다. 이는 각 열의 독립 중앙값끼리 나눈 수치와 다르다.
시도마다 속도 우열은 흔들렸고 분할은 토큰을 더 썼다. 자동 분할을 켤 근거로 사용하지 않는다.

## 모델×코어 기본 비교

같은 네 과제를 각 코어로 한 번씩 실행했다. `clamp-range`는 작은 단일 수정,
`token-bucket`은 시간·상태가 연결된 수정, `independent-pair`는 독립 기능 두 개,
`independent-four`는 문자열 정규화·범위 제한·중앙값·단위 파싱 네 기능이다.

| 모델 | 코어 | 통과 | 전체 토큰 합계 | 성공 1건당 전체 토큰: 실패 소비 포함 |
| --- | --- | ---: | ---: | ---: |
| Gemini 3.1 Pro High | V1 | 4/4 | 65,522 | 16,380.5 |
| Gemini 3.1 Pro High | V2 | 3/4 | 30,161 | 10,053.7 |
| Gemini 3.1 Pro High | V3 | 3/4 | 30,248 | 10,082.7 |
| Gemini 3.1 Flash-lite | V1 | 0/4 | 112,670 | 산정 불가: 성공 없음 |
| Gemini 3.1 Flash-lite | V2 | 1/4 | 미보고 포함 | 산정 불가: 소비 일부 미보고 |
| Gemini 3.1 Flash-lite | V3 | 1/4 | 86,649 | 86,649 |

V2 Flash-lite는 요청 21회 중 18회의 입력·출력이 보고되었다. 확인한 소비만 입력 31,677,
출력 18,669였고 나머지는 모른다. 429/네트워크 오류도 있었으므로 낮은 통과율을
전부 모델의 추론 능력 탓으로 돌릴 수 없다. 기본 비교와 반복 실험의 결과도 흔들렸다.
가격이 저렴한 모델을 연결하는 것만으로 낮은 비용에 안정적인 작업이 되지는 않는다.

V1은 네 기능 과제에서 실제 4개 워커를 실행했다. Flash-lite에서는 12회 요청 후 실패했고,
V2는 단일 공유 맥락으로 2회 요청해 통과했다. V3는 현재 실제 분할 디스패치가 없다.
따라서 V3의 이 실행을 그래프 병렬화 성공으로 기록하지 않았다.

## 실제 로컬 모델

설치되어 있던 `ollama/hf.co/HauhauCS/Gemma-4-E4B-Uncensored-HauhauCS-Aggressive:Q4_K_M`을
사용했다. 서버는 7.52B, Q4 계열, 도구 지원을 보고했다. ARM64 / 메모리 24 GiB /
논리 CPU 12개인 이 컴퓨터에서 실행했고 `/api/ps`의 실제 컨텍스트는 8,192였다.
모델을 새로 다운로드하거나 다른 서비스로 대신 실행하지 않았다.

45초 호출 제한의 초기 실험에서는 세 코어 모두 실패했다. 이후 호출 제한 90초,
전체 150초, `effort=none`으로 조정해 작은 단일 및 독립 두 기능 과제를 실행했다.

| 기본 코어 | 통과 | 성공한 작업의 승인 재검증 포함 시간 |
| --- | ---: | --- |
| V1 | 1/2 | 단일 수정 79.434초 |
| V2 | 0/2 | 성공 없음 |
| V3 | 2/2 | 단일 수정 82.818초, 두 기능 103.175초 |

V2 실험 모드의 단일 수정도 통과했지만, 두 기능 및 분할 실행은 실패했다.
현재 빌드에서 다시 실행한 두 기능의 단일+전달, 분할+전달 역시 둘 다 실패했다.
따라서 **로컬 모델로 실제 수정·검증이 가능한 것은 확인했지만, 범용 안정성이나
속도·토큰 절감은 입증하지 않았다.** V3의 2/2도 단일 관측 두 개로 과대 해석하지 않는다.

Ollama의 `prompt_eval_count`는 새로 평가한 입력만 보고한다. 전체 프롬프트 및 캐시 입력과
동일하지 않으므로 클라우드의 전체 입력 토큰과 직접 가격 비교하지 않는다.
로컬 모델의 API 이용료가 없다는 사실은 전력·장비·기다리는 시간이 공짜라는 뜻이 아니다.

## 실제로 고친 것과 아직 없는 것

- V2에 명시적인 `split_experiment`를 추가했다. 실제 별도 워커·쓰기 범위·병합 후
  단일 검증을 실행한다. 후보 2–4개와 공유 호출 여유가 필요하며 연결된 그래프는 거부한다.
  경제적 이득이 있다고 가짜 Calibration을 넣지 않았다. 기본 분할 정책은 그대로다.
- V2에 명시적인 `edit_handoff` 실험을 추가했다. 실제 변경을 Core 검증으로 전달한다.
  자동 전달은 선언 파일들이 모두 변경된 경우에만 가능하며, 부분 편집은 남은 파일을
  모델에 전달한다. 변경 없음·검증 실패·읽기 전용·쓰기 범위 위반은 승인되지 않는다.
  모델의 명시적 `propose`는 기존 프로토콜을 따른다. 이 모드는 기본값이 아니다.
- 호출 시작/종료, 최초 실제 텍스트, 종료 유형, 도구 호출/텍스트 여부를 기록한다.
  최초 텍스트가 관측되지 않으면 응답 시간으로 대체하지 않고 미보고로 남긴다.
- 호출 제한과 effort를 명시해 로컬 모델을 시험할 수 있게 했다.
- 빈 출력/출력 상한 도달을 무조건 `ungrounded prose`로 잘못 설명하던 V2 진단을 고쳤다.
- 로컬 trace에서 모델이 Core가 제공한 근거 ID를 `request_context.ids`에 넣으면
  `unknown symbol id`로 거부되던 인터페이스 불일치를 재현하고 수정했다. 이제 전달된
  근거 ID와 심볼 ID를 모두 읽을 수 있다. 경로 검사와 소스 크기 상한은 유지한다.
  이 수정은 본 벤치의 고정 바이너리 이후이므로 위 수치를 개선 효과로 주장하지 않는다.

**현재 그래프 분할은 의미적 작업 계획과 같지 않다.** V2 하위 워커는 파일 범위와
좁은 근거를 받지만 여전히 원래 전체 목표를 읽는다. 세부 목표·입출력·의존 순서·중간
성공 조건을 가진 작업 DAG와, 단위별 작은/강한 모델 선택은 이번에 검증한 기능이 아니다.
작업 난도 분해의 다음 평가는 이 구분을 유지해야 한다. AST 분할 개수만으로 성공 판정하지 않는다.

기존 Exp6 역시 분할의 고정비 때문에 시간 1.52배, 입력 1.58배였다.
[실험 원문](../experiments/effect-contract/README.md). 이번 작은 과제도 자동 병렬화보다
공유 맥락·Core 검증·도구 프로토콜 부담 제거를 먼저 검증해야 한다는 쪽의 근거다.
큰 과제에서 편집량이 충분하면 결과가 달라질 수 있으며 별도 측정이 필요하다.

## 실행과 기록

```sh
cargo build --release --manifest-path custom-tui/Cargo.toml
scripts/loom-corebench --binary custom-tui/target/release/custom-tui \
  --model omniroute/gemini/gemini-3.1-flash-lite --tasks bench/economy/tasks \
  --only independent-pair independent-four --versions v2 v2-handoff v2-split-handoff \
  --repeat 3 --jobs 1 --max-calls 12 --json /tmp/loom-economy.json
scripts/loom-corebench-report /tmp/loom-economy.json --json /tmp/loom-economy-summary.json
```

로컬은 같은 실행기에 `--model 'ollama/실제모델명' --call-seconds 90 --effort none --timeout 160`과
`LOOM_OLLAMA_CTX=8192`를 사용했다. TUI 자체의 모델 연결도 같은 공급자 어댑터를 사용한다.
실험용 분할·전달 옵션은 headless `--bench-core`에서만 켤 수 있고 기본 TUI를 바꾸지 않는다.

[클라우드 기본 비교](../bench/economy/results/cloud-summary.json),
[Flash-lite 반복 비교](../bench/economy/results/2026-10-04-lite-decomposition.json),
[로컬 기본 비교](../bench/economy/results/2026-10-04-local-matrix.json),
[로컬 재실험](../bench/economy/results/2026-10-04-local-decomposition.json).
전체 탐색/실험 JSON은 `bench/economy/results/`에 있다. 각 실행은 바이너리를 복사·고정하고
SHA-256, 설정, 실제 응답 모델, 토큰 관측, 승인·숨은 테스트 결과를 남긴다.

기본 클라우드: 모델 요청 상한 12, 시도 상한 2, 호출 45초, 전체 110초/외부 120초.
로컬: 호출 90초, 전체 150초/외부 160초. 한 서버에 로컬 과제를 동시에 보내지 않았으며
분할 실험 안에서만 하위 워커가 동시에 요청했다. 클라우드 비교는 순차 실행했다.
과제마다 코어 순서를 회전했으며 같은 반복의 기본/전달/분할 순서는 고정이었다.
따라서 순서·캐시·계정 선택의 영향을 완전히 통제하지 못했다.

개별 모델 대기 합과 병렬 대기 벽 시간을 구분한다. 병렬 대기는 시작/종료 구간의 합집합으로
측정한다. 공개 검증 시간 외 나머지에는 준비·도구·공급자 발견·프로세스 시작이 섞여 있으므로
순수 Core CPU 시간으로 부르지 않는다. 속도 표의 승인 시간에는 재검증이 포함되며,
외부 채점용 숨은 테스트 시간은 포함하지 않는다.

실행 식별자를 요청에 넣었지만 공급자 내부 캐시를 강제 해제하지 않았고 캐시 입력은 대부분
미보고였다. 일부 빌드/별도 로컬 작업과 벤치를 함께 실행했다. 세 번의 반복은 서비스 경로의
관측이며 독립적인 모델 추론 표본이나 통계적 속도 우위를 보장하지 않는다.

로컬 기본 비교의 단일 과제에 분할 실험을 잘못 포함한 1건은 즉시 거부됐고 통계에서 제외했다.
실행기는 이제 이 부적합 조합을 사전에 제외한다. 초기 전달 모드의 부분 파일 완료 결함을
고친 뒤 로컬 두 기능을 재실험했다. 이전 기록을 삭제하거나 현재 구현의 모델 실패로 포장하지 않았다.

## 남은 설계 항목과 검증

현재 V2 자동 분할 Calibration은 입력 토큰만 비교하고, 이번 실험의 완료 프로토콜도
구분하지 않는다. 이번 통계는 입력+출력을 비교하며 실험 데이터를 운영 보정값에 넣지 않았다.
자동 정책으로 채택하려면 보정값이 작업 프로토콜과도 일치하고 출력·실패 비용을 포함해야 한다.

최종 코드에서 V2 단위/통합 테스트 23개와 strict clippy가 통과했다. TUI 테스트 223개
통과(외부 환경 테스트 3개 제외), 화면 검사 442개 통과, 통계 계산 테스트 4개 통과했다.
debug/release 빌드도 끝났다. 열린 창은 재시작해야 새 코드를 사용한다.
