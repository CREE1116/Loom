# 계획·검토 검증의 오류 피드백

이전 V3는 워커의 도구 실패와 수정 결과 검증에는 피드백을 제공했지만, 계획 및
검토 응답의 역직렬화·사전 검증 오류에서는 즉시 종료했다. 모델이 `conditions`를
최상위에 넣었을 때 사용자에게 오류만 표시하고 모델에게 수정 기회를 주지 않은 것이
그 사례다.

## 수정

`control/coordinator.rs`의 Session이 계획·검토 응답을 같은 방식으로 처리한다.
잘못된 응답과 실제 검증 오류를 도구 결과로 모델에 반환하고 수정된 응답을 다시
검증한다. 모델 호출명, 스키마, DAG, 경로, 도구 인수, 읽기 전용 계약 검사를 모두
통과한 계획만 실행한다. 알 수 없는 필드를 지우거나 JSON을 임의로 재배치하지 않는다.

최대 5번의 수정 기회를 제공한다. 같은 검증 오류가 3번 나오면 더 일찍 중단한다.
새 오류가 드러나는 경우에는 그 범위 안에서 다음 수정 기회를 준다. 모든 요청은
기존의 공유 호출·토큰·시간 상한에 포함되며, 재시도 문맥에는 원래 요청과 가장 최근
실패 교환만 유지한다. 취소와 공급자 장애를 계획 형식 수정으로 재시도하지 않는다.
최종 실패에는 마지막 검증 오류와 공급자 장애 원인을 함께 남긴다.

`control/planned.rs`의 공통 검사 경로를 수정 계획에도 적용한다. 심볼 그래프는
복구 중 재사용하며, 실패한 계획의 도구는 실행하지 않는다. `control/protocol.rs`는
조건의 경로(`units[0].conditions[0]`), 문제 필드, 허용 형식을 오류에 포함한다.
예를 들어 ToolSucceeded의 path/text 혼용에는 실제 도구명을 포함한 올바른 조건
형식을 제시한다. 모델이 그 피드백으로 새 응답을 내야 하며 Core가 자동으로 고치지 않는다.

TUI는 모델에게 수정 요청을 보낸 사실을 기존 단일 대화에 표시한다. 원시 계획
응답·피드백 요청과 도구 실행은 Core 기록에 각각 남는다.

## 검증 및 한계

9개의 복구 회귀 검사는 잘못된 계획/검토, 도구 인수 누락, 단계별 진전, 반복 실패,
문맥 제한, 공유 한도, 취소, 공급자 실패와 상세 오류 경로를 확인한다. 수정 전
복구 검사는 계획·검토·사전 검증에서 실패했다. 기존 읽기 전용·잘못된 인수 검사는
모델이 같은 잘못된 계획을 반복하는 fixture로 바꿨으며, 도구 미실행과 권한 유지
검사는 보존했다.

V3 48개, TUI 226개 테스트와 화면 검사 442개가 통과했다. release PTY에서는
최상위 conditions 오류 → 모델 수정 → README 읽기 → 프로그램 설명까지 이어졌고,
수정 요청 문구도 대화에 보였다. 이 성공 경로는 deterministic fixture 검사다.

실제 로컬 Gemma Q4 모델도 오류를 받고 응답을 바꿨다. 최초 시험은 수정 횟수가
짧아 새 오류가 드러나는 중에 종료됐다. 이후 시험은 ToolSucceeded의 잘못된
파일 필드를 반복하여 조기 종료됐다. 상세 진단을 적용한 마지막 시험에서는 계획
검증을 통과했지만, 검토 응답의 잘못된 구조를 계속 수정하다 전체 180초 한도에서
응답 읽기가 시간 초과됐다. 도구 실행은 없었고 작업은 완료되지 않았다.
이는 복구 경로가 작동한다는 증거이며, 해당 로컬 모델의 과제 완료 성능을 입증한
결과가 아니다. 모델이 피드백을 항상 해결한다고 보장하지 않는다.

[실제 모델의 실패를 포함한 원시 기록](../bench/results/loom-plan-repair-2026-10-05.json)을 보존한다.
새 버전은 실행 중인 Loom을 Ctrl+Q로 종료한 뒤 `scripts/loom --backend v3`로 재시작해야 한다.
