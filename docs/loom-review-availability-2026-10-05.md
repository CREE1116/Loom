# V3 검토 모델 가용성 수정

디렉토리 분석 요청에서 계획은 만들어졌지만, 검토 단계가 `Flagship`을 필수로
요구해 도구 실행 전에 멈췄다. 저장된 실패 기록에는 Flash 모델의 정상 계획 응답과
`no model matches tier ≥ Flagship and cost ≤ Subscription` 오류가 남아 있다.
이는 검토 정책의 오류이며, 사용자가 새 키나 로컬 런타임을 설치해야 하는 상황이 아니다.

## 변경

- 검토의 최소 등급을 Local로 바꾸고, 모델 선택기에서 사용 가능한 강한 등급을
  우선한다. 강한 모델이 없을 때도 검토를 수행한다. 작업 모델 선택과 검토 모델
  선택은 계속 분리한다.
- TUI 어댑터는 모델 프로필의 가용성, 도구 지원, 비용 상한, 문맥 크기를 고려한다.
  프로필을 제공하지 않는 어댑터에는 최소 조건으로 요청한다. 사용자가 별도 검토
  모델을 지정한 경우 그 설정을 유지한다. 비용 상한을 올리거나 검토 실패를 성공으로
  취급하지 않는다. 공급자 호출 중의 장애를 해결한다고 보장하지 않는다.
- 의미적 설명이 필요한 작업은 파일 읽기 이후 워커가 근거를 해석하도록 계획 규약을
  명시했다. Semantic의 `calls`는 빈 배열이며, Tools는 구체적인 호출을 갖는다.
  `ToolSucceeded.name`의 스키마는 Registry의 실제 도구명으로 제한한다.
  요청 문구의 동작 단어나 정규식으로 실행을 결정하는 분기는 추가하지 않았다.

## 검증

작은 모델만 둔 회귀 검사에서 사용자와 같은 요청을 실행했다. 계획, 별도 검토,
README 읽기, 근거에 따른 답변까지 완료하며 이후 워커의 모델 선택도 유지한다.
수정 전에는 `scripted candidate exceeds worker constraints`로 실패했다.
강한 모델이 있을 때 우선 선택하는 검사, 비용·도구 조건을 벗어난 후보 제외,
명시적 최소 등급 유지 검사도 통과했다.

V3 테스트 39개와 TUI 테스트 226개, 화면 검사 442개가 통과했다. release PTY에서
자동 분할, 단일 대화, 실패 표시, 승인 및 재시작 복구도 확인했다.

실제 모델에서는 낯선 작은 CSV 검사 프로그램을 준비해
“디렉토리 읽어서 이게 뭐하는 프로그램인지 봐봐”를 실행했다. 첫 실행은
Semantic 계획에 도구 호출을 함께 넣어 프로토콜 검증에서 실패했다. 규약을
명시한 최종 실행은 `gemini-3.8-flash-tiered`만으로 계획·검토·소스 분석을 완료했다.
파일 목록, README, Python 소스를 읽고 `missing_rows` 함수와 CSV 결측치 검사 목적을
설명했다. 순변경은 없었고 실행 상태는 Accepted였다.

최종 실행은 모델 요청 6회, 입력 5,745 / 출력 4,504 토큰, 약 48.818초였다.
검토 호출만 약 24.657초라 여전히 비용과 시간이 든다. 이 관측은 가용성 오류가
해결됐다는 근거이며 복잡한 과제 성능이나 로컬 모델 품질의 입증이 아니다.
실패를 포함한 [원시 기록](../bench/results/loom-review-availability-2026-10-05.json)을 보존한다.

새 코드가 적용되려면 실행 중인 Loom을 Ctrl+Q로 종료하고
`scripts/loom --backend v3`로 다시 실행해야 한다.
