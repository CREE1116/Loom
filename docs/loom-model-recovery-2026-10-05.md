# 일시적인 모델 장애에서 V3 작업을 이어가기

## 확인한 원인

실패 작업 `task-v3-18db906699a42318-25074`는 아키텍처 비교 계획과 검토를
마쳤지만 첫 워커 호출의 HTTP 503에서 바로 종료됐다. 계획을 다시 만들거나
도구를 바꾸어 해결할 문제가 아니라, 실패한 모델 요청을 이어 보내야 하는 경우다.

기존 워커와 계획 세션은 공급자 오류를 즉시 반환했다. 별도 Native HTTP
어댑터는 HTTP 오류를 일반 오류 문자열로 바꾸었고, 재시도 여부를 결정할 구조가
없었다. TUI의 실제 모델 라우터에는 또 다른 문제가 있었다. 503 뒤에 경로를
20초 동안 쉬게 하면서 그 시간을 반환하지 않았으므로, 너무 이른 다음 요청은
503 대신 `Quota: every matching model is unavailable`로 실패했다.

## 변경

- V3에 `ModelFailure`와 `ModelErrorKind`를 추가했다. 재연결 여부는 오류 종류로
  판단하며, 사용자 요청이나 HTTP 설명을 정규식으로 해석하지 않는다. 기존
  ModelPort 구현은 계속 사용할 수 있고, 종류가 없는 오류는 자동 재시도하지 않는다.
- 계획·검토·워커가 같은 `CallSession`을 사용한다. 한 모델 요청에 최초 호출을
  포함해 최대 3번 시도하며 일시 장애와 속도 제한만 대상으로 한다. 인증·한도·
  잘못된 요청으로 분류된 오류는 즉시 반환한다. 모든 시도는 실제 호출 제한과
  경과시간에 포함되며, 알려진 토큰 사용량도 기존 제한을 따른다.
- 실패한 요청의 메시지와 도구 정의를 그대로 유지한다. 이미 완료한 도구,
  계획, 읽은 자료, 격리 사본의 수정 내용을 다시 실행하거나 버리지 않는다.
- 모델 라우터는 공급자가 준 대기 시간 또는 자체 경로 cooldown을 호출자에게
  전달한다. 이 시간 동안 취소를 확인하며 기다리고, 잔여시간보다 길면 원래
  장애 원인을 유지한 채 종료한다. 실패한 gateway connection 고정만 해제하며
  사용자가 지정한 모델과 비용 제한은 유지한다.
- Native HTTP 어댑터는 HTTP 상태와 Retry-After를 보존하고 잔여 실행시간에
  맞춰 네트워크 요청 제한을 줄인다. TUI 어댑터는 기존 공유 실행시간·호출별
  제한과 취소 가능한 HTTP 경로를 그대로 사용한다.
- 화면은 `모델 서버가 잠시 응답하지 않아 다시 연결하고 있습니다.`라고 알린다.
  이전에 읽거나 수정한 파일을 계속 보여주고 재연결과 도구 실패 횟수를 구별한다.
  끝내 연결하지 못하면 그 사실을 문장으로 설명하며, 원시 오류와 실행 수치는
  접힌 실행 상세와 원래 이벤트 기록에 보존한다.

## 검증

- Core의 복구 검사 9개: 계획/워커의 동일 요청 재전송, 완료한 읽기 1회 유지,
  격리 편집 유지, 계속되는 503의 3회 상한, 공유 호출 상한, 영구 오류 제외,
  Retry-After가 잔여시간보다 긴 경우, 취소, 실제 loopback HTTP 분류·시간 제한.
- TUI 어댑터 검사 2개: 실패한 gateway 연결 고정 해제와 실제 Router cooldown
  이후 복구. 후자는 수정 전에 503이 `Quota: cooling down 19s`로 바뀌며 실패했고,
  수정 후 계획 재생성 없이 완료했다.
- 화면 검사 583개 통과. 새 복구 화면의 40/80/140 너비 검사 15개를 포함한다.
  최초 새 화면 검사는 7개 실패했다. 좁은 화면에서 `UNAVAILABLE`가 줄을 넘어
  나뉘는 것을 오류로 보던 검사 하나는 원문 보존과 실제 렌더링을 각각 확인하도록
  바로잡았다. 기존 의미나 원문 보존 검사를 삭제하지 않았다.
- V1 231개, V2 23개, V3 86개, TUI 238개 테스트 통과. 실패 없음. 수동 환경 검사는
  각각 1개·1개·3개가 제외됐다. 최종 dev/release 빌드와 전체 화면 검사도 통과했다.
- 기존 V2/V3 실제 터미널 검사 통과: 병렬 워커의 단일 대화, 읽기, AST 근거,
  큰 출력 복원, 형식 교정, 셸 상태, 실패 복원, 승인·원본 적용.
- 새 실제 HTTP/터미널 검사도 통과했다. README 읽기를 성공시킨 뒤 HTTP 503과
  Retry-After 2초를 보냈다. 재연결 문장이 표시됐고 동일한 HTTP 요청으로 복구했다.
  전체 호출 4회, 계획 1회, README 읽기 1회, 재연결 1회였다. 원본은 그대로이고
  HTTP 503 및 UNAVAILABLE 원문은 이벤트에 남았다. 외부 모델 추론을 호출하지
  않는 loopback 서버다. 이 테스트가 당시 전역 모델 목록 캐시를 오염시킨 문제는
  후속 제보에서 확인해 [복원·격리 수정](loom-model-catalog-isolation-2026-10-05.md)을 적용했다.

## 실제 요청 재실행

`디렉토리 한번 훑어보고 v1, v2, v3 코어의 아키텍처 차이점을 설명해봐`를
배포용 V3와 기존 `omniroute/auto`로 실행했다.

- 작업 `task-v3-18db958e7313b088-82242`: Accepted, 46.896초, 모델 호출 5회.
- 입력 10,692 / 출력 2,900 토큰. 공급자가 캐시 토큰은 보고하지 않았다.
- 실제 도구는 디렉토리 목록 6회, README 읽기 3회, finish 1회였다.
- 도구 실패·형식 교정·파일 변경 없음. 한국어 비교 답변을 반환했다.

이 실행에서는 503이 발생하지 않았다. 실서비스에서의 재연결 성공을 주장하지
않으며, 재연결 경로는 위의 실제 HTTP/터미널 재현으로 검증했다. README와 디렉토리
구조만 읽은 비교 답변이므로 핵심 구현 전체를 검증한 아키텍처 심사로 볼 수도 없다.
한 번의 완료 결과만으로 일반 성능이나 Codex 수준의 품질을 주장하지 않는다.

## 남는 한계

계속되는 서버 장애를 없애지는 못한다. 최대 3회 또는 잔여시간 안에서 복구하지
못하면 원인을 남기고 종료한다. 실패 호출의 토큰을 공급자가 보고하지 않으면
총사용량은 미보고 상태를 유지한다. 별도 Native HTTP 경로의 날짜 형식
Retry-After는 보수적으로 자동 재시도를 중단한다. 사용자 정의 ModelPort가
시간 제한 메서드를 구현하지 않았다면 Core가 그 내부의 차단 호출까지 강제로
끊지는 못한다. 재연결 대기 중 취소는 25ms 이하 간격으로 확인한다.

실행 중인 Loom은 이전 바이너리를 계속 사용한다. Ctrl+Q로 종료한 다음
`scripts/loom-v3`로 다시 시작해야 이번 변경이 보인다.
