# Loom V5 확장 설계

상태: 2026-10-07 설계 제안. 확장 실행기와 관리 화면은 아직 구현하지 않았다.
목표는 사용자가 Loom을 다시 컴파일하지 않고 도구와 명령을 추가하는 것이다.
V4의 가벼운 직접 작업, 필요할 때만 `agent`로 전환하는 실행 계약을 유지한다.

## 현재 구조에서 바꿀 경계

`loom-core-v5/src/tools.rs`의 `specs`와 `Host::call`은 도구 목록과 실행을 고정한다.
`worker.rs`는 도구 이름으로 표시 단계와 World 갱신 여부를 결정한다.
새 도구마다 이 세 곳을 수정해야 하므로 파일 분리만으로 확장성이 생기지는 않는다.
TUI도 `app.rs`의 고정 명령 목록과 `View`로 이동한다. 설정 화면은
`custom-tui/src/app/settings.rs`로 분리돼 있지만 확장 관리 모델은 없다.

첫 구조 변경은 **도구 등록·정책·실행 결과 계약**을 만들고 기존 도구를 여기에 연결하는 것이다.
코어의 실행 루프 자체를 교체하는 공개 API는 만들지 않는다.

## 공개할 기능과 소유권

| 경계 | 확장이 제공하는 것 | Loom이 계속 책임지는 것 |
|---|---|---|
| 도구 | 이름, 설명, 인자 스키마, 결과 | 노출 여부, 검증, 예산, 취소, 기록 |
| 사용자 명령 | 설명, 입력 폼, 등록 도구로의 연결 | 명령 충돌, 입력 처리, 진행 중 실행 정책 |
| 외부 연동 | 검색·문서·서비스 등 MCP 도구 | 연결 수명, 오류 변환, 호출 표시 |
| 결과 표시 | 요약·표·진단·산출물 참조 | 배치, 접기, 색상, 포커스, 키 입력 |
| 의미적 탐색: 후속 단계 | 제한된 World 조회, 변경 제안 | 리비전, 읽기 기록, 쓰기 범위, 충돌·병합 |
| 언어 인덱서: 후속 단계 | 파싱 결과와 관계 후보 | 인덱스 캐시, 노드 식별자, 무효화 |

`agent`, `finish`, `ask`와 승인·검증·원본 적용은 코어 전용이다.
유저 명령 `/plan`, `/ask`, `/extensions` 및 기존 명령도 예약한다.
확장 명령을 모델의 `plan` 도구로 바꾸지 않는다. 자식의 재위임도 허용하지 않는다.
확장은 모델 시스템 프롬프트나 세션 히스토리를 몰래 교체할 수 없다.

## 모듈 배치와 의존 방향

첫 단계에서는 `loom-core-v5/src/extensions/` 아래에 다음 책임을 분리한다.
외부 계약이 검증된 뒤 계약 타입만 별도 `loom-extension-api` crate로 추출한다.

| 모듈 | 책임 |
|---|---|
| `manifest` | 파일 읽기, 식별자·버전·설정 스키마 검증 |
| `registry` | 도구·명령 등록, 충돌 검사, 실행별 불변 목록 |
| `policy` | 유저 설정·프로젝트 설정·역할에 따른 실제 사용 가능 기능 |
| `runtime` | 시작·호출·취소·종료, 동시 호출 제한, 장애 상태 |
| `adapters/builtin` | 기존 `Host` 도구를 등록 계약에 연결 |
| `adapters/mcp` | 외부 도구 목록과 호출 결과를 Loom 계약으로 변환 |
| `service` | 설치·활성화·설정·진단을 CLI와 TUI에 제공 |
| TUI `app/extensions` | 관리 상태를 화면·사용자 액션으로 변환 |

계약 타입은 TUI, `Overlay`, 내부 AST 타입을 의존하지 않는다.
확장 관리 서비스는 도구 실행 루프와 별도로 동작하며 TUI 없이 검사할 수 있어야 한다.
TUI와 headless CLI는 같은 서비스로 설치·설정 상태를 읽고 변경한다.
UI 설정을 코어 정책의 유일한 저장소로 사용하지 않는다.

## 도구 실행 계약

등록 항목은 스키마 외에 소유자, 지원 역할, 효과 분류, 표시 요약을 가진다.
효과는 `read`, `workspace_proposal`, `external_effect`로 구분한다.
외부 도구의 선언은 참고 정보이며 실제 권한은 Loom 정책으로 결정한다.

1. 작업 시작 시 활성 버전·설정·도구 목록을 `RegistrySnapshot`으로 고정한다.
   메인과 자식은 같은 스냅샷을 쓰되 각 역할에 맞는 도구만 받는다.
2. 모델 요청에 넣은 목록과 호출 때 검사하는 목록을 같은 등록 항목에서 만든다.
   목록에 없는 도구, 스키마 위반, 역할·권한 위반은 실행 전에 실패한다.
3. `CallContext`에는 작업·worker·호출 ID, 남은 시간, 취소 신호,
   불변 리비전, 적용 가능한 범위만 둔다. 가변 Core/AST 참조는 제공하지 않는다.
4. 실행기는 반드시 시작과 종료 기록을 짝지어 남긴다. 종료는 성공·실패·취소로
   구분하고 제한된 요약과 산출물 참조를 반환한다. 성공은 최종 작업 성공과 다르다.
5. World 읽기는 기존 `open`과 같은 실제 읽기 기록을 남긴다. 변경 제안은
   읽기 선행 조건·쓰는 파일 범위·기준 리비전을 검증한 뒤 격리 분기에 반영한다.
   이후 World를 갱신하고 기존 핸들을 만료시킨다.
6. 외부 호출은 재시도를 기본으로 하지 않는다. 부작용이 있는 호출은 타임아웃 후
   결과 불명 상태가 가능하며, 호출 ID와 증거를 남겨 중복 실행을 피한다.

`worker.rs`의 도구 이름별 단계 선택과 `change | run | agent` 갱신 분기는
등록 항목의 표시 분류와 호스트가 검증한 실행 효과를 이용하도록 이동한다.
`agent` 등 제어 흐름은 코어 핸들러로 남긴다. 등록은 같은 목록에서 관리하되
일반 확장이 제어 흐름 핸들러를 구현하거나 덮어쓸 수 없게 한다.

모든 확장 스키마를 매 턴 주입하지 않는다. 유저가 활성화한 도구 묶음만 노출하고
전체 스키마 크기에 상한을 둔다. 초기에는 관리 화면의 명시적 선택으로 충분하다.
목표별 자동 선택과 도구 검색은 실제 규모가 커질 때 추가한다.

## 외부 실행과 작성 경험

외부 도구는 별도 프로세스의 MCP 서버를 어댑터로 연결한다. 사용자 입장에서는
manifest와 실행 가능한 서버가 있으면 등록할 수 있고 Rust 코드 변경이 필요 없다.
언어별 SDK는 필수가 아니다. Rust 동적 라이브러리 로딩은 초기 범위에서 제외한다.

MCP의 도구 목록·호출은 기존 계약을 재사용한다.
Loom manifest는 배포 정보, 설정, 명령 연결과 Loom 정책을 담당한다.
프로토콜 버전은 어댑터가 지원하는 명시적 버전을 고정해 검사한다.
Loom API 버전과 MCP 버전은 별도로 관리한다.
[MCP 도구 계약](https://modelcontextprotocol.io/specification/2025-11-25/server/tools),
[MCP 전송 계약](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)을 참고한다.

별도 프로세스는 장애 격리에 유용하지만 파일·네트워크 접근을 제한하는 샌드박스는 아니다.
첫 버전의 로컬 실행형 확장은 유저가 명시적으로 등록한 신뢰된 프로그램으로 취급한다.
프로젝트에서 발견한 manifest만으로 실행하지 않는다. 자식과 `/ask`에는 외부 실행형
확장을 기본적으로 노출하지 않는다. 읽기 전용·쓰기 범위를 실제로 강제할 수 있는
실행기 또는 호스트 중개 어댑터가 준비된 기능만 후속 단계에서 연다.
MCP의 읽기 전용 선언만으로 이러한 제약이 보장된다고 판단하지 않는다.

도구 식별자는 `ext_<고유 설치 키>__<도구 키>`로 만든다. 표시 이름은 별도다.
제공자 이름을 단순히 정규화하다 충돌하는 경우도 검사한다.
Core와 backend별 도구 이름·길이 제약을 함께 검사하고 조용히 잘라내지 않는다.

다음은 예정된 manifest 형식의 예시이며 현재 로더가 지원하는 설정은 아니다.

```json
{
  "manifest_version": 1,
  "id": "local.docs",
  "name": "문서 검색",
  "version": "0.1.0",
  "loom_api": 1,
  "runtime": {
    "kind": "mcp_stdio",
    "command": "python3",
    "args": ["server.py"]
  },
  "tools": ["search_docs"],
  "commands": [
    {"name": "docs", "tool": "search_docs", "input": "query"}
  ]
}
```

상대 인자 경로의 기준은 설치된 확장 디렉터리이며 shell 문자열로 실행하지 않는다.
위 `docs` 명령은 문자열 입력을 도구의 `query` 인자로 연결한다.
임의의 도구 인자는 설정 스키마에서 입력 폼으로 표현한다.
지원하지 않는 manifest/API 버전은 명확한 호환성 오류로 표시한다.
처음 실행 시 발견한 도구 중 manifest의 허용 목록만 등록한다.
도구 설명·스키마 변경도 새 등록 세대로 취급한다.

## 설치·설정 수명

로컬 디렉터리에서 추가하는 경로부터 구현한다. 설치 시 파일을 버전별 관리 디렉터리에
복사하고 manifest·내용 해시를 저장한다. 활성 버전은 원자적으로 갱신하는 포인터로 관리한다.
실행 중에는 해당 버전과 설정의 참조를 유지해 수정·삭제로 실행이 달라지지 않게 한다.
개발용 원본 연결은 이후 명시적 개발 모드로 추가한다.

유저 설치 목록과 프로젝트 활성화·설정은 분리한다. 프로젝트에서 유저 권한을
넓힐 수 없으며 동일 ID의 로컬 확장이 설치된 다른 확장을 자동으로 덮어쓰지 않는다.
설정 값은 스키마로 검증하고 비밀 값은 로그·작업 기록에 포함하지 않는다.
관리 화면에는 요청 권한과 실제 적용 권한을 구분해서 보여준다.

활성화·업데이트는 다음 작업부터 적용한다. 현재 DAG와 병렬 질문의 버전은 고정된다.
비활성화는 신규 작업에서 제외하고 진행 중 호출 상태는 별도로 표시한다.
현재 호출 중단은 명시적 취소 액션으로 제공한다. 삭제는 활성 참조가 끝나면 정리한다.
장애 확장의 자동 무한 재시작은 하지 않으며 다른 확장과 코어는 계속 동작해야 한다.

작업 영구 기록에는 설치 ID·버전·내용 해시·설정 세대·도구 키를 남긴다.
복원은 기록을 보여주는 동작이고 확장 호출을 재실행하는 동작이 아니다.
확장이 삭제돼도 과거 요약과 실패 기록을 읽을 수 있어야 한다.

## 확장 관리 화면

진입점은 `/extensions`와 설정의 `확장 관리` 항목이다. 전용 관리 화면으로 이동하며
채팅 영역에 설치 목록이나 설정 JSON을 반복 출력하지 않는다.
현재 backend가 해당 확장을 실행할 수 있는지도 상태에 반영한다.

```text
확장                          [+ 로컬 확장 추가]
검색 …

  문서 검색       활성       도구 1개
  프로젝트 진단   비활성     도구 2개
  이슈 연동       오류       설정 필요

↑↓ 선택   Enter 상세   Esc 돌아가기
```

상세에는 설명, 설치 버전·출처, 이 프로젝트의 상태, 도구·명령, 설정, 실제 권한,
최근 오류를 보여준다. 일반 목록에는 오류 요약 한 줄만 둔다.
활성화·비활성화·설정·제거는 상세에서 실행하고 성공·실패·다음 작업 적용 상태를 표시한다.
상세의 실행 기록도 기본은 요약이며 인자·원문·프로세스 로그는 펼쳐서 본다.
비밀 값을 가리고 터미널 제어 문자열을 제거한 후 표시한다.

넓은 화면은 목록과 상세를 나란히 보여주고, 좁은 화면은 목록 → 상세로 이동한다.
`Esc`는 상세 → 목록 → 이전 화면 순서로 돌아간다. 키보드로 모든 동작을 할 수 있어야 한다.
관리 화면을 여는 동작은 진행 중 작업과 `/ask`를 중단하지 않는다.
확장 UI는 처음에는 공통 요약·표·폼으로 제한한다. 임의 키 이벤트나 렌더러 코드를
등록시키지 않아 TUI 포커스와 정보량을 Loom이 책임지게 한다.

## 구현 순서와 완료 조건

1. **내장 도구 등록 경계**: 기존 도구·역할·실행 결과를 registry에 연결한다.
   도구 이름 충돌, 노출과 호출 정책의 일치, 내장 기능 회귀를 검사한다.
2. **사용자 확장 한 개의 전체 경로**: 로컬 추가 → manifest 검사 → MCP 연결 →
   도구 선택 → 메인 호출 → 시작/종료 표시 → 영구 기록 → 비활성화까지 완성한다.
   작은 문서 검색 예제와 작성 안내를 함께 제공한다.
3. **관리 화면**: 위 서비스를 연결해 목록·상세·설정·활성화·제거를 실제 동작으로 구현한다.
   새 화면 검사를 먼저 실패시킨 뒤 구현하고 48/80/120열 화면·PTY·기존 UI 검사를 실행한다.
4. **World를 사용하는 확장**: host 조회와 변경 제안 계약을 추가한다.
   실제 읽기 추적, 오래된 리비전 거부, 자식 범위 위반 거부, 병렬 질문 쓰기 거부를 검사한다.

외부 프로세스 종료·응답 지연·취소 무시·과도한 출력·잘못된 결과·도구 목록 변경을
프로토콜 fixture로 검사한다. 활성 작업 중 버전 변경, 삭제 후 기록 복원,
