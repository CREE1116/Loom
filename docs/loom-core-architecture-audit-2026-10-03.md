# LOOM Native Core 구조 점검 (2026-10-03)

코드와 기존 실행 기록에 근거한 점검이다. 화면 렌더링 속도와 독립적으로 Core의 작업
계약, 실행 소유권, 근거 전달, 완료 판정이 의도대로 작동하는지를 살핀다.

## 구현과 증거

- `loom-core/src/control.rs`: Core가 revision, 작업 상태, Overlay 검증 및 원본 적용을
  소유한다. `ExecutionMode`는 현재 `Single`뿐이다.
- `loom-core/src/worker/mod.rs`, `worker/agents.rs`: Worker 모델이 직접
  `spawn_agent`/`merge_agent`를 호출할 수 있다. 자식의 파일 범위 충돌과 병합은
  검사하지만, Core의 Split Gate가 분할 결정을 내리는 경로는 구현되지 않았다.
- `loom-core/src/context.rs`: `derive`는 요청문의 정확한 단어와 심볼 이름 및 요청에
  등장한 파일 경로로 계약을 만든다. `compile`은 anchor 본문과 연관 시그니처를 담는다.
  이름을 언급하지 않은 변경, 신규 테스트, 잠금 파일을 선제적으로 포착하지 못한다.
- `loom-core/src/worker/mod.rs`: 단일 응답에 도구 호출이 없고 아직 수정하지 않았다면
  설명 응답으로 종료할 수 있다. 자연어 메시지의 변경 의무를 결정적으로 판별하는
  별도 `TaskIntent`는 현재 없다. Edit 요청의 무변경 응답에도 적용되는 경로이므로
  작업 성공 판정의 의미를 API 수준에서 명확히 해야 한다.

기존 실험 `loom-core/measurements/free-model-notes.md`의 12개 소규모 작업에서
기본 실행과 Context Compiler 실행 모두 12/12를 통과했다. 원격 입력 토큰은
162,011 대 162,076으로 사실상 같았고 계약 recall은 0.472였다. 이 결과는
Context Compiler의 일반적인 효율을 증명하지 못하며, 대규모 작업으로 일반화할
수 없다. `docs/loom-experiment-findings.md`의 38개 분할 실험에서는 병렬 방식의
총 실행 시간이 단일 방식의 1.52배였다. 따라서 분할의 가능성과 유익성은 구분한다.

## 이번에 적용한 수정

1. 실패한 제안을 재시도할 때, 기존 lexical contract만 넘기던 handoff에
   `scope_feedback`(계약 밖 변경 포함), `observed_write_files`를 추가했다.
   검증 실패 후 재개하는 실험으로 실제 수정 파일을 다음 Worker가 볼 수 있음을 증명했다.
   이는 **사후 피드백**이다. 최초 계약의 recall이나 자동 작업 분해 정확도를 높였다는
   의미는 아니다.
2. Context Compiler가 빈 문자열을 만들었을 때 로컬 그래프 anchor 힌트를
   막는 경로를 수정했다. 내용이 없는 context를 전달하지 않고 기존 로컬 탐색
   힌트를 보존한다. 이 수정만으로 remote-token gate 통과를 주장하지 않는다.

## 다음 설계 변경의 선행 조건

**1. 실행 결과의 계약부터 명시한다.** Surface가 `Answer`, `Inspect`, `Edit`처럼
요청 결과를 명시적으로 전달하고 Core가 이를 보존해야 한다. `Edit`는 patch가
없으면 성공으로 판정하지 않고, `Inspect`는 승인·코드 수정을 요구하지 않아야 한다.
자연어 키워드만으로 작업 종류를 추측해 성공 조건을 결정하는 방식은 피한다.
기존 일반 대화 사용성을 위해 미지정 요청의 처리 정책을 별도로 정의하고 시험한다.

**2. 그래프는 권위 있는 관측과 구분한다.** `find/near`와 심볼 관계는 후보와
명시된 파일 범위의 근거다. 실제 read/write 집합은 Overlay에서 관측하고,
검증·충돌 판정은 관측한 파일과 revision을 기준으로 한다. 미지정 파일과 신규
테스트는 모호한 상태로 남겨 두고, 계획 오류를 결과 상태에 기록한다. 후속 시도는
관측된 집합을 이전 계획에 합쳐야 한다. 이번 변경은 이 인계의 첫 단계다.

**3. 오케스트레이션 권한을 정리한다.** 현재 `Single` 결정과 모델의 임의
자식 생성이 동시에 존재한다. Core가 분할을 결정하는 설계를 택한다면, Worker는
Core가 만든 작업 단위와 scope만 받아 실행하고, 자식 제안은 Core의 계획 변경
요청으로 취급해야 한다. 먼저 단일 Worker와 명시적 2-Worker의 동일 작업 실행을
측정하고, 고정비·중복 맥락·실제 수정 범위·검증 성공을 수집한다. 관측 없이
병렬 Worker를 기본값으로 도입하지 않는다.

**4. 컨텍스트는 불변 revision에 연결한다.** 초기 slice를 보낸 후 Worker가
같은 내용을 재독하는 원인을 기록하고, 제공한 source span과 새 revision의
일치 여부로 내용 재사용을 결정한다. 빈 slice, 수정 후 무효화, 세션 압축 후 원문
복원 등을 각각 검증한다. 평가 대상은 큰 다중 파일 작업으로 확장한다.

이후 비교는 별도의 모델 품질 평가를 포함해야 한다. 작은 12개 작업의 통과율,
TUI 자체 점검, 리그레션 테스트만으로 Core 아키텍처의 품질을 판정할 수 없다.

## 후속 안정화 구현 (2026-10-03)

- Core의 명시적 `TaskIntent`(Auto/Answer/Inspect/Edit)와 CLI `--intent`를 추가했다.
  `Edit`는 자연어 설명만 내고 끝내면 성공하지 못한다. `Inspect`와 `Answer`는
  읽기 전용이며 기존 Native TUI 제출은 호환성을 위해 아직 Auto를 쓴다.
- 재시도 전체의 실행 예산에 맞춰 **각 검증 명령에도 잔여시간**을 전달한다.
  모델 호출은 첫 요청 90초, 이후 45초를 기본 제한으로 두고 Router의 여러
  공급자 시도 전체가 그 제한을 공유한다. 모든 시간은 실제 경과시간이다.
- 게이트웨이의 응답 헤더가 연결 ID를 알려주면 다음 호출에서 고정하고,
  실패하면 해제한다. 전체 모델 대기, 보고된 upstream 시간, gateway overhead를
  Worker trace와 모델 원장에 각각 기록한다. 자기개선 분석기는 보고된 gateway
  overhead가 30초 이상인 사건을 환경 지연으로 보고하며, 인프라 사건만 있는
  작업을 코드 자가수정 대상으로 택하지 않는다.
- HTTP 취소를 받아 기다리던 Worker가 빠르게 반환하는 동작은 재현했다. 다만
  ureq의 차단 중인 네트워크 소켓 자체를 즉시 중단하는 기능은 아직 없다.

**여전히 열려 있는 설계 과제:** TUI에서의 명시적 작업 의도 선택, Core가
분할과 작업 범위를 결정하는 그래프 오케스트레이션, 실제 게이트웨이의 연결
고정 헤더 호환성 확인, 실제 모델로 동일 작업을 반복한 완료율·원격 입력 토큰
비교, HTTP 수준의 적극적 요청 중단. 각각은 별도 증거와 회귀 테스트를
갖춘 뒤 채택해야 한다.
