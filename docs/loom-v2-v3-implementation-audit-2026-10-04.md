# V2 / V3 구현 점검 — 2026-10-04

V3는 V2를 확장한 상위 버전이 아니라 별도로 만든 구현이다. 작은 편집 벤치 통과는
큰 저장소 탐색, 작업 분해, 작은 모델의 일반적 신뢰성을 증명하지 않는다.
현재 두 구현 모두 원래 목표인 의미 기반 작업 DAG를 완성하지 않았다.

## 구현 차이

| 항목 | V2 | V3 |
| --- | --- | --- |
| 하위 라이브러리 | V1의 인덱스·언어 추출·모델·effects 자원 재사용, 작업 루프는 독립 | 별도 타입·인덱스·effects·모델·작업 루프; TUI에서는 공통 공급자/Validator 주입 |
| 인덱스 | 파일 digest별 심볼 캐시, 이름 기반 참조와 경계 후보 | 현재 `CodeGraph::build`는 Rust 파일만 처리; 최상위 선언 위주, impl 메서드·중첩 모듈 처리 미흡 |
| 맥락 | inventory와 제한된 근거 ID, 최근 도구 교환, 현재 diff를 구성 | 언급된 파일·심볼에서 사전 맥락; 워커에서는 전체 messages를 매번 재전송 |
| 병렬 워커 | 비교 측정으로 허용하면 실제 격리 워커 실행·병합·단일 검증; 실험 강제 옵션 별도 | SplitGate 후보만 계산; 실제 디스패치·병합 없음 |
| 도구 확장 | Tool trait와 등록 레지스트리, 공통 권한/효과 계약 | 도구 목록 함수와 dispatch match를 함께 수정해야 함 |
| 분석 판정 | 전달한 근거 인용 요구, 구현 주장에 코드 근거 강제 | 읽기 전용 워커의 답변을 완료로 수락; 근거 인용 검사 부족 |
| 공통 | 격리 편집, Core 검증, 승인·재검증·원본 변경 검사 | 동일한 기본 안전 경로 구현 |

V2의 자동 분할은 동일 revision·모델·그룹에 맞는 성공 비교 3쌍을 요구한다.
일반 새 과제에서는 거의 단일 실행이다. 판정은 현재 입력 토큰만 비교하며, 출력·실패 비용과
작업 프로토콜을 함께 묶는 개선이 필요하다. 실험 결과를 운영 보정값으로 넣지 않았다.

## V3에서 남은 핵심 구현

1. **의미 기반 계획과 실행:** 하위 목표, 입력·출력, 의존성, 중간 성공 조건, 파일 경계,
   하위 작업별 모델 선택을 갖춘 DAG와 실행기가 없다. 파일별 그룹 후보는 이를 대신하지 못한다.
   SplitGate의 `_world`는 실제로 사용하지 않으며, 현재 후보 판정도 그래프 독립성 검사와 다르다.
2. **정확한 인덱스와 맥락:** 그래프는 호출을 타입으로 해석하지 않고 토큰에서 이름을 근사한다.
   `span_lines`는 선언 식별자의 span을 사용하므로 ContextCompiler의 “full anchor”가
   함수 본문 대신 이름 위치 한 줄일 수 있다. 앵커 없는 프로젝트 개요 요청에는 맥락이 비기도 한다.
   맥락 상한도 추가 후 검사하므로 엄격한 byte 상한이 아니다.
3. **메모리와 토큰 제어:** WorkMemory에 관찰을 기록하지만 요약을 다음 모델 요청에 쓰지 않는다.
   전체 도구 출력과 메시지가 누적되며, 동일 호출 반복을 막는 실행 게이트가 부족하다.
4. **계약 감시:** ScopeMonitor는 존재하지만 Core 실행 루프가 호출하지 않는다.
   명시된 쓰기 파일은 도구에서 제한하되, 요구된 동작의 완결성·누락 여부는 별도 판정하지 못한다.
5. **실패 기록과 자기개선:** task/attempt/metrics는 저장되지만 모델·도구 교환 전체를 재생하는
   상세 trace와 자동 진단→재현→개선→비교 판정 루프가 V3에 통합되어 있지 않다.

## 실제 실패 기록

- V2 `run-gWCPkG`: “디렉토리 살펴봐”가 Analyze로 분류됨. 심볼 216,912개 인덱싱에
  약 21.6초, 모델 요청까지 약 38.4초. 로컬 모델 45초 timeout으로 총 약 83.4초 후 실패.
- V2 `run-jeM8yW`: 모델의 프로젝트 구성 설명을 문서 근거만 인용했다는 이유로
  `report_findings`가 거부했다. 뒤이어 공급자 HTTP 503으로 종료했다.
  단순 목록 요청에 구현 분석의 판정 기준을 적용한 것이 Core 쪽 오류다.
- V3 `task-v3-18db4b1cb0e81b68-15084`: 프로젝트 파악 요청, 모델 요청 5회, 약 108초.
  로컬 모델 timeout 이후 쿨다운 상태를 즉시 두 번 더 호출했다. 새 코드 수정 시도로
  모델 연결 장애를 복구하려 한 것은 실행 정책의 문제다.
- 사용자가 언급한 권한 오류는 정확한 문구를 확인하지 못했다. 사용자의 요청으로
  해당 건을 점검 범위에서 제외했으며, 원인을 확정하거나 고쳤다고 주장하지 않는다.

## 이번에 수정한 범위

- TUI의 정확한 단순 목록 요청(`디렉토리 살펴봐`, `list PATH`, `:inspect list PATH` 등)을
  Inspect로 분류하여 모델 호출 0회로 처리한다. “무슨 프로젝트인지 분석해” 같은 해석 요청은
  이 규칙으로 완료를 가장하지 않고 기존 의미 작업 경로로 보낸다.
- V2는 Git 사본에서 사라지는 빈 디렉토리도 보여주도록 실제 소스 디렉토리를 읽기 전용으로
  조회한다. 기존 실행 준비·사본 생성 비용은 여전히 남아 있다.
- V3는 단순 목록을 AST/워커/격리 사본 없이 처리하고 결과를 Core 이벤트에 저장한다.
  revision 캡처를 위한 파일 순회 비용은 남는다. 독립 CLI도 이 요청에는 모델 endpoint를 요구하지 않는다.
  CLI JSON에도 실제 결과 summary를 포함한다.
- V3의 list_dir도 공통 경로 검사로 traversal·절대 경로·메타데이터·symlink를 거부한다.
- V3는 ModelFailed를 패치 실패와 구분하여 해당 실행을 즉시 중단한다.
  공급자 어댑터 내부 재시도나 향후 다른 모델로의 복구 정책까지 구현한 것은 아니다.

회귀 검사: 두 TUI 백엔드에서 미신뢰/읽기 전용 목록 조회, 0회 모델 호출과 결과 저장,
V3 provider 실패의 단일 호출 종료, 경로 탈출 거부, Core 재개, endpoint 없는 CLI 목록 조회.
실제 PTY에서 목록과 호출 수 표시, 기존 승인·재시작·반영 경로를 함께 확인한다.

우선순위는 탐색/분석 계약 분리 → V3 인덱스·함수 본문 맥락 수정 →
제한된 작업 상태와 반복 감지 → 의미 기반 DAG 실행·작업별 모델 선택이다.
현재의 버전 숫자로 우열이나 실사용 완성도를 판단하면 안 된다.
